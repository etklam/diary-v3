# [133] Compress API responses

Status: ready-for-agent
Execution: done
Published: 2026-10-25
Completed: 2026-10-25

Category: bug
Type: Capacity
User stories covered: None directly; every authenticated read and every public article
fetch pays the cost.

## Observation

No layer in the request path compresses an API response. Verified three ways on 2026-10-25:

**Structurally.** `apps/api/src/app.ts` mounts no compression middleware and the package
never imports `hono/compress`. `ops/nginx/production.conf` has no `gzip` directive on its
`/api/` location. No manifest under `ops/k8s/` declares a Traefik `compress` middleware, and
Traefik does not compress without one. The apex domain resolves to a single A record outside
the Cloudflare anycast ranges, so DNS is not proxied and no edge compresses on the way out
either.

**At runtime.** The real app, built with the sanctioned fixture upstream
(`apps/api/src/market-data/fixture.ts`) so no database is required, serving the real
`/api/market/historical` route through the real middleware chain:

| Request | `content-encoding` | Bytes |
|---|---|---|
| `Accept-Encoding: gzip, deflate, br` | *(none)* | 12,217 |
| Same body behind `hono/compress` | `gzip` | **2,072 (−83.0%)** |
| Behind `hono/compress`, no `Accept-Encoding` | *(none)* | 12,217 |

The decompressed payload is byte-identical, and a client that does not negotiate an encoding
is unaffected. A second ratio data point on JSON this repo generates:
`openapi/openapi.json` is 2,233,598 bytes raw and 114,073 gzipped (−94.9%).

The fixture price series is more regular than live quotes, so 83% is the optimistic end for
that endpoint; the 70–85% band is the defensible expectation for this app's JSON.

**The contrast is the argument.** The Web tier already does this well — `@react-router/serve`
mounts `compression()` and fingerprinted assets ship `immutable, max-age=1y`. The API tier
simply never got the same treatment, so `/api/timeline`, `/api/reviews`, `/api/blog`,
`/api/market/historical` and `sitemap.xml` all travel uncompressed.

## Requested outcome

API responses negotiate compression, with the SEC download routes explicitly excluded, and
before/after byte counts recorded as runnable evidence.

## Implementation plan

**1. Mount `hono/compress` on the API.** Register it in `apps/api/src/app.ts` with a 1 KiB
threshold, inside the request-id middleware so the request log still wraps the whole
response. Hono's default `COMPRESSIBLE_CONTENT_TYPE_REGEX` already excludes
`application/zip`, so the SEC package and batch routes are skipped and keep their
`Content-Length`.

**2. Exclude the SEC single-document download explicitly.** That route
(`apps/api/src/sec-filings.ts`) passes the upstream `content-type` through, which is often
`text/html`, so content-type filtering alone would compress it — dropping the
`Content-Length` the handler computes from the staged file and inserting a transform into a
stream whose backpressure and cleanup are deliberately engineered. Declare
`Cache-Control: no-transform` on those responses: it is the standard signal for a
byte-exact body, and `hono/compress` honours it through its `shouldTransform` check. Prefer
this over a path deny-list, which would drift as routes are added.

**3. Prove it with a test.** A unit test over the real app and the real
`/api/market/historical` route asserting that a negotiating client receives
`content-encoding: gzip` with `Vary: Accept-Encoding`, that a non-negotiating client
receives the identical uncompressed body, that the decompressed payload matches byte for
byte, and that a `no-transform` response is passed through untouched.

**Verification:** `npm run lint`, `npm run typecheck`, the new unit test, and the recorded
before/after byte counts for a representative endpoint.

## Provisional acceptance criteria

- [x] A negotiating client receives a compressed body with `Vary: Accept-Encoding`; a non-negotiating client receives the current bytes unchanged.

## What was built

`apps/api/src/response-compression.ts` — a `responseCompression()` middleware the API owns,
mounted as the outermost middleware in `apps/api/src/app.ts`. `apps/api/src/sec-filings.ts`
now declares `no-transform` on its three attachment kinds while metadata keeps plain
`no-store`. Covered by `tests/unit/api-response-compression.test.ts`.

**Why not `hono/compress`.** It was mounted first, and that is how the defect below was
found: `hono/compress` can only apply its size threshold to a response that declares a
`Content-Length`, and Hono's `json()`/`text()` helpers do not — `@hono/node-server` fills
that header in later, at the socket, long after the middleware has decided. The threshold
was therefore dead, and measured on the real app every small response was encoded at a
loss:

| Response | Before | With `hono/compress` |
|---|---|---|
| `/healthz` | 15 bytes | 35 bytes |
| 404 error JSON | 120 bytes | 152 bytes |

The owned middleware reads only as far as the threshold: a body that ends inside it is
replayed verbatim and its length declared, and a larger one streams through the encoder from
where the peek stopped, so no response is buffered whole. Negotiation (`parseAccept`) and
the compressible-type list (`COMPRESSIBLE_CONTENT_TYPE_REGEX`) are imported from Hono rather
than reimplemented. `Number(null) === 0` was the second trap: an absent `Content-Length`
read as a zero-byte body and suppressed all compression; the header is now null-checked
before being compared.

### Acceptance — 2026-10-25

Measured over a real HTTP listener (`@hono/node-server`), not just `app.fetch`, because the
socket layer is where `Content-Length` and chunked framing are decided:

| `/api/market/historical?symbol=AAPL&range=1y` | `Content-Encoding` | Framing | Bytes |
|---|---|---|---|
| `Accept-Encoding: gzip` | `gzip` | chunked | **2,072** |
| No `Accept-Encoding` | — | `Content-Length: 12217` | 12,217 |
| `/healthz`, `Accept-Encoding: gzip` | — | `Content-Length: 15` | 15 |

The gzipped body gunzips to bytes identical to the uncompressed response, and a standard
`fetch` client decodes it transparently into the same 320 data points. A `deflate`-only
client gets `deflate` (2,060 bytes); an `identity` client gets the original bytes.
