# [131] Bound the SEC metadata cache by bytes, not entries

## Observation

The 2026-09-27 audit already found and recorded this, and left it open by design
(`docs/audits/project-cleanup-2026-09-27.md:89`):

> SEC metadata caches limit entry counts (250 submissions, 500 historical segments and 500
> filing indexes), not retained bytes. With a 5 MiB response ceiling and indexes retaining
> both JSON and HTML, the theoretical cache budget exceeds the 768 MiB pod limit. No
> representative-corpus or cgroup test established a practical out-of-memory failure here.

The relevant code is `apps/api/src/sec-edgar/cache.ts` and its consumers in
`apps/api/src/sec-edgar/service.ts`. The audit's own sizing is the argument: an entries-only
cap multiplies by an unbounded entry size. 500 filing indexes that each retain JSON **and**
rendered HTML, at up to a 5 MiB response ceiling each, is a worst case far above the 768 MiB
pod limit — the cache cannot evict its way out because it counts the wrong thing.

The audit was right to refuse to claim a failure it did not measure, and none has occurred.
This ticket exists because "no representative-corpus test established a failure" is a reason
not to panic, not a reason to leave a documented unbounded path in a memory-constrained
process.

## Requested outcome

A metadata cache whose retention is bounded by bytes with eviction, plus the capacity
evidence the audit asked for.

## Implementation plan

**1. Add a byte budget to the cache.** Track retained size per entry (the actual bytes held —
JSON string plus HTML when both are kept), evict by LRU or the existing policy once a
configurable ceiling is crossed, and keep the entry-count caps as a secondary limit. Expose
the ceiling as configuration with a conservative default derived from the pod limit.

**2. Measure a representative corpus.** The audit's synthetic SEC resource runner
(`scripts/parity/performance-sec-resources.mjs`) is the pattern to extend: generate a corpus
sized near the worst case, drive the metadata read path, and report peak RSS and cache bytes.
The `docs/audits/project-cleanup-2026-09-27-resources.json` file is the template for the
recorded evidence.

**3. Prove eviction.** A test that fills the cache past its byte budget and asserts that
retained bytes stay bounded and that an evicted entry is re-fetched rather than returned
stale.

**Verification:** the byte-budget test passes; the corpus run reports a peak RSS below the
768 MiB pod limit with the budget enforced; the evidence is recorded next to the existing
resource JSON.

### Acceptance — 2026-10-25

`SecCacheBudget` in `apps/api/src/sec-edgar/cache.ts` bounds all four metadata caches
**together** — the audit's concern was the sum, and four caches each under a generous ceiling
can still exceed the pod. Default 64 MiB, configurable through `SEC_CACHE_MAX_BYTES` and
documented in the environment contract. Entry-count caps remain as secondary ceilings.
Retained size is charged per entry as its serialized wire bytes, which is directly comparable
to the client's 5 MiB response ceiling. Eviction walks the inserting cache's LRU end and
stops at one entry rather than emptying itself, so the total is bounded by the ceiling plus
one entry per cache.

**The audit's theoretical concern turned out to be measurable.**
`scripts/parity/performance-sec-metadata-cache.mjs` drives 120 companies × 4 filings — 600
metadata reads, each filing index retaining 4 MiB — through the real service, recorded in
[`docs/audits/sec-metadata-cache-2026-10-25.json`](../../../docs/audits/sec-metadata-cache-2026-10-25.json):

| Configuration | Peak retained | Peak process RSS |
| --- | --- | --- |
| Entry caps only (pre-change) | **2,041 MiB** | 1,111 MiB |
| Shared 64 MiB budget | 63 MiB | 557 MiB |

The pre-change run exceeds the 768 MiB pod limit in RSS alone, so this was a reachable
failure and not only an arithmetic one. The audit paragraph now points at this evidence.

`tests/unit/sec-cache-budget.test.ts` (8 tests) proves retained bytes stay bounded while
the entry cap is nowhere near reached, that an evicted entry is **re-fetched rather than
served stale**, that a fresh hit still serves from memory, that the count cap still applies,
that one budget accounts across caches, and that replacing an entry releases its bytes.

Gates: lint, `tsc --noEmit`, `npm run test:unit` **142 files / 1253 tests**, and both
artifact builds pass.

**Not done.** No cgroup-enforced out-of-memory test was run, and peak RSS in both runs
includes the fixture's own transient 4 MiB payloads, so it is an upper bound on the cache's
contribution rather than a measurement of it.
