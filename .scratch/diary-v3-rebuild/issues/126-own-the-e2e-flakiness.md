## Observation

[117](117-remaining-e2e-failures.md) established the principle — "a suite that answers
differently each time cannot answer the question it is run to answer" — and fixed the
drift it could name. What it could not fix, and what no ticket now owns, is the *process*
that keeps producing it. Two datapoints from the record:

- `docs/audits/project-cleanup-2026-09-27.md:43` — the full Chromium suite ran
  **256 passed / 8 failed in 20.7 minutes**, and one failure (PWA controller) "did not
  reproduce in three separate browser probes". That failure is neither fixed nor explained;
  it is recorded.
- [117](117-remaining-e2e-failures.md), "Provisional acceptance criteria" and "Execution record" — the confirming run
  was **337/1**, the one failure a 90-second timeout in `partner-timeline-parity.spec.ts:146`
  on a loaded machine, passing 7/7 on rerun.

The suites are large (≈90 specs) and slow (20–36 minutes), which is exactly the environment
where flakiness is easiest to shrug off and most costly: it erodes trust in green, and the
nightly regression workflow ([124](124-gate-changes-before-main.md)) is where a flake looks
like a real failure. Today there is no retry policy, no quarantine list, and no per-run
flake count — a rerun-to-green is indistinguishable from a fix.

## Requested outcome

A number, published each run, for "how flaky was this suite," and a rule for what happens
to a case that flakes.

## Implementation plan

**1. Turn on retries in CI only, and report them.** `playwright.config.ts` can set
`retries: process.env.CI ? 1 : 0` and Playwright already records `flaky` outcomes. Surface
the flaky count in the run summary so a retried pass is visible as *flaky*, never as a
clean pass.

**2. Emit a small per-run artifact** listing the spec, test title, run duration and
outcome for anything that failed-then-passed. This is the raw material for a trend.

**3. Define the quarantine rule.** A case that flakes more than once in N runs is moved to
a named `@flaky` list with a linked ticket, runs out of the blocking set, and cannot be
deleted or skipped silently. This is the enforcement that makes [117](117-remaining-e2e-failures.md)'s
principle survive contact with the next deadline.

**4. Characterise the two known suspects first** — the PWA controller case audit:43 records
as never reproducing, and the `partner-timeline-parity.spec.ts:146` 90s timeout. Both want a
deterministic seam (a held request, an injected clock) rather than a longer timeout, which
is what [117](117-remaining-e2e-failures.md) already prefers.

**Verification:** two consecutive full runs report a flake count; a deliberately introduced
timing race (a throwaway experiment) shows up as `flaky`, not as `passed`, in the artifact.

### Acceptance — 2026-10-25

`tests/support/flake-reporter.ts` runs in the Chromium and WebKit critical configs, prints
a flake count every run **including zero**, and writes
`playwright-report/flaky-<suite>.json` with spec, title, project, attempt count, each
failed attempt's duration and a one-line failure summary that distinguishes a timeout from
an assertion. The artifact is named per suite because both run sequentially in one CI job.

Retries: `process.env.CI ? 1 : 0` in the Chromium and WebKit configs; **zero always** on
the release gate, with the reason stated in `playwright.release.config.ts` — that gate
decides whether a built image ships, so a retried pass there would hide a release defect
rather than a timing race.

The quarantine rule is written in
[`docs/operations/e2e-flakiness.md`](../../../docs/operations/e2e-flakiness.md): more than
one flake in ten consecutive runs quarantines a case; quarantining means a `@flaky` tag, a
register row with evidence and a ticket, and exclusion from the blocking set; deletion,
`test.skip` and `test.fixme` are forbidden; leaving quarantine requires a deterministic
seam, not a longer timeout. The mechanism is live — `test:e2e:blocking` runs
`--grep-invert @flaky` as the gating step and a separate non-blocking
`test:e2e:quarantine` step keeps quarantined cases running, because unblocking is not the
same as not looking.

Covered by `tests/unit/flake-reporting.test.ts` (6 tests), which feeds the reporter a
synthetic failed-then-passed case and asserts it is recorded as flaky and never as a clean
pass.

**Not done — step 4 and the two-run verification.** The PWA controller case and the
`partner-timeline-parity.spec.ts:146` timeout are entered in the register as **carried,
not reproduced**, with the evidence that exists. Characterising either needs PostgreSQL and
two full 20–36 minute browser runs, neither available here, so no run of this reporter has
produced a flake count yet. The register says so explicitly rather than implying the cases
were investigated. The PWA case is deliberately **not** tagged `@flaky`: three probes could
not reproduce it, and quarantining on historical evidence would remove a passing check from
the blocking set.
