# [136] First use is decided by seven requests, so a new account sees a loading dashboard

## Observation

`overview.tsx:943` gates the welcome screen on every resource the page will ever need:

```
const allResourcesReady = Boolean(
  timezone && !timezoneError &&
  loaded(attention) && loaded(reviews) && loaded(recent) &&
  loaded(valuation) && loaded(plans) && loaded(watchlist),
)
const firstUse = allResourcesReady && isOverviewFirstUse({ … })
```

`firstUse` is therefore `false` for the whole load, and the `false` branch
(`overview.tsx:1004-1023`) is the complete dashboard: attention, recent decisions, portfolio,
watchlist, destinations. A brand-new account's first screen is five regions of "Loading…",
which then collapse into a two-paragraph welcome. The layout shifts once, at the worst
possible moment, and the reader's first impression of a decision journal is an empty
dashboard loading.

**The failure mode is worse than the latency.** `loaded()` (`overview.tsx:565`) requires
`!error`. Any one of the resources failing leaves `firstUse` permanently `false`, so the
welcome screen is replaced by five sections of error notices and retry buttons — on an
account that has no data to fail on. Zero-data accounts are exactly where the valuation and
attention projections are most likely to reach an edge, so the state most in need of a
welcome is the state least likely to get one.

**Seven requests, one of them duplicated.** The page issues six
(`overview.tsx:333-346` plus the `/api/auth/me` at `:921`), and `root.tsx:190` has already
fetched `/api/auth/me` for the same session to resolve `viewer`. Two identical requests on
every workspace navigation, and the second one gates the welcome screen. `Shell` already
passes `viewer` down through the outlet context (`root.tsx:470`, `ShellOutletContext`), and
`viewer` carries `id` and `role` but not `timezone`, which is why Overview refetches.

## Requested outcome

A new account sees the welcome screen as the first thing the page paints, and it still
appears when a supporting section fails.

## Implementation plan

**1. Decide first use on one cheap fact.** An account with no diaries is a new account. The
`recent` resource already answers it — `recent.data.pagination.total === 0` — and it is the
first of the six to resolve because `/api/diaries/summary?limit=3` is the smallest query of
the set. Render the welcome as soon as that one resource says zero, without waiting on the
other five.

The broader `isOverviewFirstUse` check (`overview-logic.ts:138`) is not wrong, it is
answering a different question: "is this account empty in every dimension?" Keep it, and
keep its unit tests, but demote it from a gate to a refinement — it can decide whether the
destinations block is shown alongside the welcome, which is a cosmetic choice, not whether
the welcome appears at all.

**2. A failing section must not suppress the welcome.** Once first use is decided by the
diary count alone, a failed valuation or watchlist cannot reach that decision. Make the
dependency explicit rather than incidental: if `recent` itself fails, fall back to the
dashboard branch, because a failed count is not evidence of an empty account.

**3. Remove the duplicate `/api/auth/me`.** Extend `ShellOutletContext` so `viewer` carries
`timezone` alongside `id` and `role`, and have `overview.tsx` read it from the outlet context
instead of issuing its own request. The retry path (`overview.tsx:978`) then needs to
revalidate the shell's fetch rather than its own; a `revision`-keyed refetch in `Shell` is
the smaller change. Confirm no other consumer of `ShellOutletContext` breaks.

**4. Hold the skeleton rule.** `DESIGN.md` Components specifies skeletons for initial loads
of list and table surfaces. The welcome branch has no list, so it needs no skeleton — it
should simply not render the dashboard it is about to replace.

**Verification:** `npm run lint`, `npm run typecheck`, `npm run test:unit`
(`tests/unit/overview-logic.test.ts` covers `isOverviewFirstUse`), `npm run design:check`.

## What was built

`isOverviewFirstUse` now takes nullable resources: the diary count is required and decisive,
the other five are optional refinements where *unresolved means unknown, not empty*. The
welcome renders as soon as `/api/diaries/summary` reports zero, and a failure anywhere else
can no longer suppress it. Five new unit cases cover the partial-resolution matrix, including
the case that must stay false — an unresolved diary count is not evidence of an empty account.

The duplicate `/api/auth/me` is gone. `ShellOutletContext` now carries
`viewer: { id, role, timezone }` plus `viewerError` and `refreshViewer`, and `Shell` parses the
response with `authUserResponseSchema` rather than reading it untyped. Overview dropped its
own effect and its three pieces of timezone state; the retry button calls `refreshViewer`.
