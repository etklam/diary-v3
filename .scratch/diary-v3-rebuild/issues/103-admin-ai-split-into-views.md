# [103] Split AI administration into task-scoped views

Status: needs-triage
Execution: todo
Published: 2026-10-06

Category: enhancement
Type: Design follow-up
User stories covered: AI Reports V1 administration. Provider configuration, prompt versioning, per-user access, usage and audit.

## Observation

Found during the [whole-app page score](../../../docs/design/ui-page-score-2026-10-06.md),
where `/admin/ai` scored **38/100** — the lowest of all 69 route states.

**It is the longest page in the app at 4,051px, and it is one undivided surface.** In
reading order: a site-wide generation switch, worker heartbeat, provider configuration
(14 fields), a nested `Pricing (estimates only)` fieldset, a nested `API key` fieldset
with three radio options, two prompt editors each with a large textarea and four actions,
an Access table with a per-row checkbox, quota input and Save, a Usage & audit section
with its own month filter and a nine-column table, and an audit log.

**Save scope is unknowable from the screen.** Three draft-save submit buttons render:
one for the provider at `admin-ai.tsx:506`, and two more from `(['weekly','monthly'] as
const).map(...)` at `:523`, each rendering its own form's submit at `:530`. Add Publish,
Publish new version, Restore default template, Run paid test, Paid test (synthetic data),
Load model list, and a per-row Save in the Access table, and the page carries roughly a
dozen mutation controls with no visual grouping that tells you which one commits which
region. Several of them cost real money.

**The kill switch is 4,000px from what it governs.** "Allow generation site-wide" sits in
the first 150px. Nothing below it changes appearance when it is off, so an administrator
cannot tell from the configuration area whether any of it is currently live.

**Nested fieldsets render as boxes inside the page.** `DESIGN.md` is explicit: "a card
nested inside a card degrades to a plain block, because nested cards are always wrong."
The Pricing and API-key fieldsets are exactly this.

**The usage table's headers wrap to three lines each** — "Reserved cost (cents)",
"Unknown outcome", "Estimated cost (cents)" — because nine columns are squeezed into the
content width.

Against the cognitive-load checklist the page fails single focus, chunking, visual
hierarchy, one-thing-at-a-time, minimal choices and progressive disclosure — six of eight.

## Requested outcome

Split AI administration into task-scoped views so that each view has one job, one save
scope, and a visible statement of whether the feature is currently live. Preserve every
existing capability, the revision/publish model, the confirmation dialogs on paid and
destructive actions, and the content-free guarantee (administrators never see other
users' report content).

## Implementation plan

For triage — the split is the decision, so this is a proposal rather than a settled plan.

**1. Decide the split.** Four candidate views, matching the four jobs: **Provider**,
**Prompts**, **Access**, **Usage & audit**. Either four routes under `/admin/ai/*` with a
shared sub-navigation, or one route with tabs. Routes are preferred: they are linkable,
they keep each view's data fetching independent, and they match how `/admin/research`
already separates settings from runs.

**2. One save scope per view.** A view commits one thing. The Access table's per-row Save
is legitimate (it is per-user state), but it must be the only save in its view.

**3. Make the live state ambient.** The site-wide switch and the worker heartbeat become a
status region that is visible from every AI admin view, and the configuration reflects
when generation is off rather than looking identical either way.

**4. Unnest the fieldsets.** Pricing and API key become ruled regions within their view,
per the Structural Hierarchy Rule, not boxes inside a box.

**5. Bound the usage table.** Put it in a named scroll region with a per-page minimum
width so the page does not widen and headers stop wrapping to three lines — the same
treatment [104](104-admin-accounts-rebuild.md) applies to the accounts table.

**6. Keep paid actions distinguishable.** "Run paid test" and "Paid test (synthetic
data)" spend money. They should not sit at the same visual weight as Save draft, and
their existing `window.confirm` guards stay (or become the project dialog — see the
DESIGN.md note that confirmations use the project dialog, never `window.confirm`, which
this page currently violates at `:294`, `:337`).

**Verification:** existing `/admin/ai` e2e coverage is updated for the new route or tab
structure and must pass. New coverage asserts that each view saves only its own region,
that the live-state region appears in every view, and that the usage table scrolls within
its region without widening the page at 768px.

## Provisional acceptance criteria

- [ ] AI administration is split into task-scoped views; no single view exceeds roughly one-and-a-half viewports at 1440×900.
- [ ] Each view has exactly one save scope, except the Access table's documented per-row saves.
- [ ] Whether generation is currently enabled is visible from every AI admin view without scrolling.
- [ ] No fieldset or card is nested inside another card; grouping uses rules and space.
- [ ] The usage table lives in a named, focusable scroll region; no header wraps to three lines, and the page does not widen at 768px.
- [ ] Paid actions are visually distinguishable from free ones and keep an explicit confirmation naming the cost.
- [ ] Confirmations use the project dialog rather than `window.confirm`.
- [ ] Every existing capability is preserved: provider draft/publish with revision checks, model list loading, prompt versioning and restore-default, per-user grants and quotas, usage aggregation, audit log.
- [ ] Administrators still cannot see other users' report content.
- [ ] Verified in all three locales, light and dark, at 390/768/1440, keyboard-only.
