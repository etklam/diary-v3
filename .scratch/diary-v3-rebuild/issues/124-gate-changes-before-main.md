## Observation

This ticket opens a quality-hardening set (124–132) filed from an audit of the
repository on 2026-10-16. The audit ran the source gates directly: `tsc --noEmit`
clean, `npm run lint` clean, `npm run test:unit` **134 files / 1198 tests pass in 16s**,
and `npx vitest run tests/integration/diary-editor.test.ts` **7/7** against real
PostgreSQL. The code is in good shape; the governance around it is the gap.

**Nothing gates a change before merge.** Read the triggers:

- `.forgejo/workflows/deploy.yml` is `on: push: branches: [main]` and runs
  `lint`, `typecheck`, `test:unit`, `contracts:check`, `manifests:check` and the
  blocking release smoke (`.forgejo/workflows/deploy.yml:56-68,112-125`). These gates
  are real and blocking — but they run **after** the commit is already on `main`.
- `.forgejo/workflows/regression.yml` is `on: schedule` + `workflow_dispatch` and owns
  `test:integration`, full Chromium, WebKit critical and the extended release artifacts
  (`.forgejo/workflows/regression.yml:2-5,73-117`). They gate nothing on the deploy path.
- **No workflow declares `pull_request`.** `grep -rn "pull_request" .forgejo/` returns
  nothing, and `grep -rn "continue-on-error" .forgejo/` also returns nothing.
- **`design:check` runs in no workflow at all.** Four scripts — contrast, the Figure
  Rule, native edges and register assignment (`package.json:18`) — pass locally and are
  never enforced in CI, even though earlier tickets (122, 120) created them precisely to
  stop drift.

Two consequences. A branch can merge with only post-merge verification, so a red `main`
is the first signal rather than a blocked PR. And a change that breaks integration or the
browser suites still deploys: those tiers only report the next night.

**One documentation defect belongs here too.** `docs/audits/project-cleanup-2026-09-27.md:87`
states the CI policy "keeps integration, full Chromium, WebKit and release-artifact checks
advisory (`continue-on-error: true`). A failed tier can still be deployed." That was true
before `3e5535c ci: move expensive regressions off deploy path`; today they are blocking
*within* the nightly workflow and simply do not gate deploy. The audit paragraph now
describes a mechanism (`continue-on-error`) that exists nowhere in the tree, which is worse
than a stale number — a reader looking for it will not find it. `docs/operations/ci-cd-notes.md:25-30`
already describes the current arrangement correctly, so the two documents disagree.

## Requested outcome

A change is verified before it reaches `main`, and a red gate cannot be mistaken for a
deployment blocker that does not exist.

## Implementation plan

**1. Add a pre-merge workflow.** A new `.forgejo/workflows/ci.yml` on `pull_request`
running the cheap, deterministic gates: `lint`, `typecheck`, `test:unit`,
`contracts:check`, `design:check`, `manifests:check`. These already run in seconds to a
couple of minutes and need no services, so this is additive and low-risk.

**Require the checks in branch protection.** A failing workflow alone does not prevent a
merge or direct push. Configure the authoritative Forgejo `main` branch to require the
pre-merge job's status and restrict bypass/direct pushes. Record the exact required status
context and the repository-side setting as evidence; workflow YAML cannot establish this.

**2. Put `design:check` into the deploy path as well,** so a direct push to `main` (not
only a PR) cannot ship a contrast or register regression.

**3. Decide the integration/e2e policy explicitly** rather than leaving it implied:
either (a) a merge requires the last nightly regression on that SHA to be green, or
(b) `test:integration` joins the pre-merge gate and the browser suites stay nightly.
Integration alone takes a few minutes against disposable PostgreSQL and is the higher-value
half. Record whichever is chosen in `docs/operations/ci-cd-notes.md`.

**4. Correct the audit paragraph** so it names the real arrangement (nightly, blocking
within its own workflow, not on the deploy path) instead of `continue-on-error`.

**Verification:** open a throwaway PR that fails `lint`, confirm CI fails and the protected
branch rejects its merge, then confirm a passing PR can merge;
confirm `design:check` appears in a workflow's step list; confirm the audit and
`ci-cd-notes.md` describe the same policy.
