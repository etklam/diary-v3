## Observation

`apps/api/src/app.ts` is 535 lines and does three jobs at once:

1. **Middleware and cross-cutting concerns** — request id, body-length limit, CORS, the
   authentication middleware (`app.ts:266-325`), CSRF, the bounded body read, not-found and
   on-error handlers (`app.ts:499-532`).
2. **Composition of the shared services** — rate limiter, auth session service, market data,
   the research evidence provider and search budget, the AI report service, the account
   email lifecycle (`app.ts:153-200,356-478`).
3. **~55 route registrations in one flat block** (`app.ts:377-497`), interleaved with two
   inline route definitions. `registerDiaryRoutes(app, { db, now })` at 495 is a registrar
   call with a smaller dependency set, not an inline route definition.

The route block is the maintenance cost. Every new endpoint edits this one file, adding a
line to a list of 55 where the ordering constraints are real but undeclared — the file's own
`diary-routes.ts:1-6` comment warns that literal segments must register before `:id`
parameters, and `app.ts:433-437` repeats it for Guru slugs. Those comments are the only
record of an ordering requirement that a 55-line block makes easy to violate. Adding a
route is also a merge-conflict magnet: two concurrent features both append near the bottom.

This is not a correctness problem — the app runs and all gates pass. It is the single
place the architecture's "code boundaries" (`docs/architecture.md`) stop applying, and it
scales badly with every remaining ticket.

## Requested outcome

A composition root that reads as a table of contents — middleware, services, and grouped
route registration — with the ordering constraints it depends on stated where they live.

## Implementation plan

**1. Split the route block into grouped registrars** by domain, each a function that takes
`app` and the dependency bundle: e.g. `registerDiarySurface`, `registerPortfolioSurface`,
`registerMarketSurface`, `registerGuruSurface`, `registerAdminSurface`,
`registerResearchSurface`, `registerAuthSurface`. Group, don't rewrite — each group calls the
existing `register*Routes` functions in the same order it does today.

**2. Keep one authoritative ordering comment per group** where literal-before-parameter
matters (the diary and Guru cases), so the constraint travels with the code it constrains.

**3. Leave sequencing visible in the root.** `app.ts` should still show, in order, the
middleware a request passes and the top-level order the groups register in — the point is to
make the file a summary, not to hide the order in seven files.

**4. Keep dependency requirements explicit.** Group registrars may receive the shared
context, but leaf registrars should retain the dependencies they actually use.
`registerDiaryRoutes(app, { db, now })` does not need unused error helpers merely to make
its call look like its neighbors.

**Verification:** `tsc`, `lint`, `test:unit` clean; `test:integration` green — the route
surface is unchanged, so the integration suite is the regression proof. Confirm the reserved
Guru path ordering is still exercised by the existing Guru tests.
