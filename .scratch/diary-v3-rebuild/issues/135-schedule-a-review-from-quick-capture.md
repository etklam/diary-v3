## Observation

The product's stated sequence is three steps: record, connect evidence, review. The third
step is the only one that makes the product something other than a notebook, and it is the
only one that can reach back out to the reader — a due review is the single event this
product raises on its own.

`reviewDueAt` exists only in the full editor. `diary-editor.tsx:111` carries it in
`scalarFields` and `:919` resolves it from the review-time inputs. `quick-composer.tsx` has
no such field anywhere; grep returns nothing but the Markdown `preview` state.

Quick capture is not a side path. It is the path every entry point leads to:

| Entry point | Destination |
|---|---|
| `diary-navigation.tsx:88` — mobile bottom bar, first slot | `/diaries/quick` |
| `quick-entry.tsx:109` — the global ⌘/Ctrl J shortcut | the capture dialog |
| `quick-entry.tsx:37` — the sidebar's one filled action | `/diaries/quick` |
| `overview.tsx:830` — first-use "Start recording" | `/diaries/quick` |
| `overview.tsx:991` — the Overview header action | `/diaries/quick` |

The full editor reaches the reader through exactly one visible affordance: an unlabeled
chevron (`quick-entry.tsx:62`, see [139](139-workspace-help-and-capture-paths.md)).

After the write, `QuickSavedState` (`quick-composer.tsx:298`) offers four actions — open the
diary, edit details, new note, return to company research. None of them schedules anything.
"Edit details" is technically the path to `reviewDueAt`, but it is named for the mechanism,
sends the reader into a 1,489-line editor, and nothing on the way says that a review date is
what is missing.

**The consequence is systemic, not local.** An account captured entirely through the quick
path has `reviewDueAt IS NULL` on every row. `apps/api/src/diary-list.ts:54` filters pending
reviews on `lte(diaries.reviewDueAt, now)`, so the review queue stays empty, `useReviewCount`
reports zero forever, the sidebar badge never appears, and
`overview.tsx:645` shows "No current actions" permanently. The reader concludes the product
has nothing to tell them, which is true, and which is a design defect rather than a fact
about their portfolio.

## Requested outcome

A reader who captures a note through the quick path can set a review date without leaving
the saved state, in one click, and the loop closes from the default path.

## Implementation plan

**1. Schedule after the save, never before it.** The control belongs in `QuickSavedState`,
not in the composer. Low-friction capture is the first principle this surface was built on
(`DESIGN.md`, Page recipes — Diary authoring), and a required decision before submit would
cost exactly what the quick path exists to save. After the save is also the moment the
reader still holds the judgment in mind and can answer "how long until this is testable?"
at its lowest cost.

**2. Three presets and nothing else.** One week, one month, one quarter, resolved against
the account timezone. A fourth "custom" choice would reintroduce a date picker into a
four-button row; a reader who wants a specific instant already has "Edit details", which
stays. Three is inside the working-memory bound and matches the one real question being
asked.

**3. Use the endpoint that already exists.** `PATCH /api/diaries/:id/review-schedule`
(`apps/api/src/diary-review.ts:71`) takes `{ reviewDueAt, expectedRevision }` and already
sets `reviewStatus` to `pending`. No API change, no contract change, no migration.
`diaryResponseSchema` (`packages/contracts/src/index.ts:723-725`) carries `revision`, so the
create response from `quick-composer.tsx:809` already holds everything the PATCH needs —
thread `revision` through `onSaved` alongside the id rather than issuing a read first.

**4. Keep one filled action.** `QuickSavedState`'s comment already states the rule: "One
filled action at the one moment the flow is finished; the rest stay quiet." The scheduler is
a labelled row of three `.quiet-button .button-compact` controls under the existing action
row, not a fourth filled button. On success it collapses to a `role="status"` line naming
the scheduled day; on failure it keeps the controls and shows the reason.

**5. Both containers get it for free.** `/diaries/quick` (`routes/quick.tsx:17`) and the
⌘J dialog (`quick-entry.tsx:167`) both render `QuickSavedState`, so one change covers both.

**Verification:** `npm run lint`, `npm run typecheck`, `npm run test:unit`,
`npm run design:check`. An e2e case asserting that a quick-captured diary appears in the
review queue after scheduling requires PostgreSQL.

## What was built

`QuickReviewSchedule` in `quick-composer.tsx`, rendered by `QuickSavedState` so both
containers — `/diaries/quick` and the ⌘J dialog — get it from one change. Three quiet
`.button-compact` controls under the existing action row; the saved state still has exactly
one filled action.

**The presets are durations, not calendar dates.** +7 / +30 / +90 days from the moment of the
click, as instants. That is exact without any zone or DST reasoning, it is the honest unit for
"come back to this", and the confirmation still names the resolved day in the account's own
calendar via `calendarDateInTimezone`, so the reader sees what the duration became. The
alternative — calendar months in an arbitrary IANA zone — needs a local-day-to-UTC converter
this codebase does not have; `trade-time.ts` is device-zone only.

One `PATCH /api/diaries/{id}/review-schedule` per click, using the revision the create
response already carried. `onSaved` now hands back `SavedDiary` (`id`, `revision`, `timezone`)
instead of a bare id, which is the only reason any extra data crosses the boundary. No API,
contract, schema or migration change.
