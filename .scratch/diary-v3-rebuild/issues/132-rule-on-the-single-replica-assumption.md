# [132] Rule on, and record, the single-replica assumption

## Observation

The system behaves correctly only as long as there is exactly one API process, and this is
recorded as an open boundary rather than a decision
(`docs/audits/project-cleanup-2026-09-27.md:88`):

> The default in-memory rate limiter and in-process schedulers assume the documented single
> API process. This audit does not establish multi-replica capacity.

The code makes the assumption in several places, none of them obviously wrong on their own:

- `apps/api/src/rate-limit/` ships a memory store and a Redis store; the app defaults to the
  **memory** runtime (`app.ts:153` `injectedRateLimiter ?? createMemoryRateLimitRuntime()`).
  In-process counters are per-replica: two replicas each permit the full limit, so the
  effective limit doubles. With Redis the runtime is shared, which is precisely why the Redis
  path exists.
- In-process schedulers — the SEC shared scheduler (`createPostgresSecSharedScheduler`), the
  research/search budget and worker loops — coordinate through Postgres or not at all
  depending on the path.
- Realtime Socket.IO (`socket.io`) keeps connection state in the process that holds the
  socket.

The source manifest configures one API replica, and the audit is explicit that no
multi-replica capacity was established. The constraint is already documented in
`PRODUCT.md` ("Capabilities and Constraints") and `ops/k8s/production/README.md`
("Layout notes"): one active API process owns scheduling and realtime. The remaining gap
is enforcing that boundary and recording what must change before scaling. Someone who
scales `deployments/diary-v3-api` to two replicas will not be stopped
by any gate, test or manifest, and will silently weaken rate limiting and possibly duplicate
scheduled work.

## Requested outcome

A written ruling — single replica is a hard, enforced constraint, or multi-replica is a
supported target with the work listed — and a guard so the assumption cannot be broken by
accident.

## Implementation plan

**1. Take the ruling.** Either (a) **single replica is authoritative**: name it in
`docs/architecture.md` and the production overlay README, and reject API replica counts
other than one in the release validator; or (b) **multi-replica is a goal**: file
the follow-on work (require Redis rate limiting, move every in-process scheduler to a
Postgres/Redis-backed lease, decide Socket.IO affinity or a Redis adapter) and describe it as
a program, not a flag flip.

**2. Enforce whichever is chosen.** If (a), add a manifest/validation check — the existing
`scripts/validate-production-manifests.ts` is the natural home — that fails if the API
replica count differs from one while the single-process boundary remains authoritative.
Redis alone cannot authorize multiple replicas: schedulers and Socket.IO remain
process-local. For (b), keep that guard until the scheduler/realtime acceptance work is
complete. Future multi-replica configuration must require `RATE_LIMIT_BACKEND=redis`;
`auto` can fall back to per-process memory and is insufficient for shared enforcement.
Check the actual startup configuration in `server.ts`, not only `createApp`'s injectable
memory default. The production manifest currently selects `auto`; that does not establish
the live cluster's Redis state or grant scaling support.

**3. Record the decision** in `docs/operations/environment-contract.md` and the relevant ADR
so the audit footnote can point at a decision instead of standing alone.

**Verification:** the ruling is written where scaling is configured; a manifest with
`replicas: 2` fails the check even with `redis` while the single-process boundary applies;
the audit's open boundary is updated to reference the ruling. Only a separately accepted
multi-replica implementation may relax that guard.
