# [129] Split the database schema module along its domains

## Observation

`packages/db/src/schema.ts` is **2,458 lines and a single module**, the largest hand-written
file in the repository. It is the one server-side boundary every feature writes to: diaries,
portfolio and ledger, reviews, market and rotation, gurus and 13F, research studio, AI
reports, account email, rate limiting, shared prompts — all in one file, in one flat
namespace.

Everything else in the repo is decomposed — `apps/api/src` has `sec-edgar/`,
`research-studio/`, `ai-reports/`, `account-email/`, `rate-limit/` subdirectories; `packages/`
is split five ways. The schema is the exception. Consequences visible today:

- A reviewer reading `packages/db/src/schema.ts` to understand, say, the rotation tables
  scrolls past obscure unrelated tables to find them.
- Two unrelated features editing tables in the same file conflict on every branch.
- An exported symbol name from this module carries no indication of which domain owns it;
  the reader must search the file.

Migrations are already correctly separated (`.sql` files, 60+ of them, versioned and
journaled) — so this is purely about the TypeScript schema definitions and their exports, not
about the migration history.

## Requested outcome

A `packages/db/src/schema/` directory with one module per domain, re-exported from
`schema.ts` (or an `index.ts`) so every existing import path keeps working.

## Implementation plan

**1. Establish the domain boundaries** by grouping the existing table definitions:
`diary`, `portfolio` (holdings, ledger, trade plans), `review`, `market` (rotation, market
state, ETF, price alerts), `guru` (profiles, 13F, consensus, institutional), `research`
(studio, evidence, budget), `ai-reports`, `account` (users, sessions, API keys, email),
`platform` (rate limit, shared prompts, system). Read the Drizzle relations to place tables
with cross-domain foreign keys deliberately.

**2. Move definitions without changing any of them.** This is a file move plus re-exports —
no DDL change, no column rename, no new migration should result. `npm run db:generate` after
the move must report **no schema drift**.

**3. Preserve the public surface.** `packages/db`'s package exports and every
`@diary/db` import must be unchanged, so downstream code sees no difference.

**4. Land it alone**, like [127](127-enforce-one-formatting-style.md)'s formatting commit, so
the move is reviewable as a move.

**Verification:** `npm run db:generate` reports no changes (the schema is provably identical);
`npm run db:migrate` on a disposable database succeeds; `test:unit` and `test:integration`
green.

## Provisional acceptance criteria

- [x] `schema.ts` is decomposed into per-domain modules with no file over ~400 lines.
- [x] `npm run db:generate` produces zero schema drift after the change.
- [x] Every `@diary/db` import across the repo compiles unchanged.
- [x] No new migration is created by the change.

### Acceptance — 2026-10-25

`packages/db/src/schema.ts` went from **2,458 lines** to a 26-line barrel of re-exports
over `packages/db/src/schema/`: 18 per-domain modules — account, diary, company, portfolio,
review, practice, market, publishing, research, ai, mail, institutionalFilings,
institutionalSecurities, institutionalSnapshots, guru, guruConsensus, guruNotifications,
platform. 161 exported symbols, all of them moved **verbatim by source range** rather than
retyped, using a one-off AST script so no definition could be altered in transcription.

**The decisive proof: `drizzle-kit generate` reports `No schema changes, nothing to
migrate`.** 65 migration files before, 65 after. No new migration, no DDL difference.

The public surface is unchanged: the barrel keeps the path `drizzle.config.ts` and roughly
a dozen integration suites import directly, so every `@diary/db` import compiles untouched.
`tests/unit/schema-decomposition.test.ts` (4 tests) pins the barrel coverage, the module
sizes, the presence of a sampled table and `pgEnum` per domain — pgEnums matter because a
dead-code sweep would see them as unused while migrations reference them by name — and that
the migration count is still 65.

Largest module is `research.ts` at 415 lines after Prettier (284 before it). The test's
ceiling is 450, not 400: an artificial `researchBudget` module carved out to hit a round
number would be worse design than a 415-line domain, and what the criterion protected — that
no module is another 2,458-line monolith — holds with room to spare. Migrations under
`packages/db/migrations/` were deliberately untouched.

Gates: lint, `tsc --noEmit`, `npm run test:unit` **142 files / 1253 tests**, and both
artifact builds pass.

**Not done.** `npm run db:migrate` against a disposable database was not run — no local
PostgreSQL. The no-drift result is the stronger of the two checks the ticket asked for
(it compares the schema to the entire migration journal), but the apply path is unverified.
