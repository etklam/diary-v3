# [104] Rebuild the admin accounts page around a readable table

Status: needs-triage
Execution: todo
Published: 2026-10-06

Category: bug
Type: Design follow-up
User stories covered: Admin account inventory and role management.

## Observation

Found during the [whole-app page score](../../../docs/design/ui-page-score-2026-10-06.md),
where `/admin/users` scored **44/100**. It also carries the only whole-page horizontal
overflow found anywhere in the app.

**The search control is structurally broken.** `routes/admin-users.tsx:121`:

```jsx
<div className="admin-users-section-heading">
  <h2 id="admin-users-list">{c.users}</h2>
  <form className="admin-users-search">
    <label htmlFor="admin-users-search">{c.search}</label>
    <div><input id="admin-users-search" …/><button type="submit">{c.searchAction}</button></div>
  </form>
</div>
```

The heading row puts the `h2` and the whole search form side by side, and inside the form
the label is a sibling of a `div` wrapping input and button. Rendered at 1440px, the
label "Search email or name" lands on the *Accounts* heading baseline around x≈890, the
input floats *above* it at x≈1090, and the Search button sits *below* the input. Label,
field and button occupy three different lines across two columns. The association is
correct for assistive technology (`htmlFor` is right) but visually the label does not
read as belonging to the field.

**The page overflows horizontally at 768px.** Measured in-browser:
`documentElement.scrollWidth` 784 against `clientWidth` 768, with offenders
`form.admin-users-search`, its wrapping `div`, its `input`, and
`table.admin-users-table` extending to **1104px**. `DESIGN.md`: "Wide tables live in
named, bordered, rounded scroll regions with page-specific minimum widths; the page
itself never widens to fit a table." There is an `.admin-users-table-wrap` at `:123`, but
it is not containing the table at this width.

**The table centres its content.** Headers and cells both render centre-aligned, so
emails wrap mid-address — "research-" / "member@example.test" — and the Diaries count
column is centred rather than right-aligned. A data table reads left-aligned for text and
right-aligned for figures.

**"Accounts" is printed twice** — once as the `h2` at `:121`, once as the table
`<caption>` at `:123`.

**Four full-weight danger buttons sit in the densest part of the page.** `:123` renders
`className="secondary danger-button admin-users-delete"` per row, so every account row
carries a bordered red "Delete account" at full button height, beside a greyed per-row
"Save". `DESIGN.md` asks row controls to stay quiet-weight so they do not compete.

**"System counts" is a four-up stat row** — Total users, Total Diaries, Total alerts,
Total transactions. `DESIGN.md` names this exactly: "`.stat` … four of them side by side
is the hero-metric template, not a design," and "Prefer `.ledger` to a row of stat
tiles."

**The current-account row breaks the row rhythm**: "Current account / You cannot change or
delete your own account." is crammed into the Actions cell as two lines of prose where
every other row has a button. The guard is correct and must stay; its presentation is the
problem.

Credit where due: the page converts the table to stacked cards at 390px and that
conversion is good. The desktop layout is the defective one.

## Requested outcome

Rebuild the page so the search control reads as one control, the table is left/right
aligned by content type inside a bounded scroll region that cannot widen the page, row
actions stop competing, and the counts use the ledger idiom. Preserve every behaviour:
the current-account guard, role changes with their confirmation, deletion with its
consequence copy, the search, and the recent-diaries table.

## Implementation plan

**1. Rebuild the search as one control.** Label above field, field and submit on one row,
the whole thing as a single block — not interleaved with the section heading. If the
heading and the search must share a row, the search becomes a self-contained group within
it rather than three loose children.

**2. Contain both tables.** Put each in a named scroll region with a page-specific
minimum width, and verify at 768px that `scrollWidth === clientWidth`. This is the
measured bug, so the test for it is a width assertion, not a screenshot.

**3. Align by content type.** Email and name left, Role and Actions left, Created and
Diaries right. Drop the duplicate caption or drop the `h2` — keep whichever serves
assistive technology better and name the other differently.

**4. Quiet the row controls.** Role Save and Delete account become quiet-weight row
controls. Delete keeps `danger` semantics, its consequence copy and its confirmation —
`DESIGN.md` requires all three — but stops rendering as the loudest element in the table.

**5. Replace the stat row with a ledger line.** Four `.ledger-row`s, or one line of
figures, instead of four tiles.

**6. Give the current-account row the same shape as the others.** A short status label in
the Actions cell, with the full explanation available as a description rather than two
lines of prose inline.

**Verification:** `tests/e2e/admin-users.spec.ts` is updated and must pass, with added
assertions for no horizontal page overflow at 768px and 390px and for the preserved
current-account guard. Note the pre-existing failing case recorded in the
[2026-09-06 layout review](../../../docs/design/ui-consistency-review.md) — a synthetic
diary returns 201 and appears in recent diaries but the account row reports a diary count
of 0. That is a data defect, not a layout one; do not "fix" it by weakening the
assertion, and do not treat it as caused by this work.

## Provisional acceptance criteria

- [ ] The search label, field and submit read as one control group on one alignment line at 1440, 768 and 390.
- [ ] `documentElement.scrollWidth` equals `clientWidth` on this route at 390, 768 and 1440; both tables scroll inside their own named regions, which are keyboard-focusable.
- [ ] Table text is left-aligned and figures are right-aligned; no email wraps mid-address at 1440.
- [ ] The page names "Accounts" once in visible copy.
- [ ] Row-level Save and Delete are quiet-weight; Delete keeps its danger semantics, consequence copy and confirmation dialog.
- [ ] System counts render as a ledger rather than four stat tiles.
- [ ] The current-account row has the same structure as every other row, and the guard still prevents self role-change and self-deletion.
- [ ] The 390px stacked-card conversion still works.
- [ ] Verified in all three locales, light and dark, keyboard-only, at 200% zoom.
- [ ] The pre-existing diary-count mismatch is neither fixed nor masked here; it is left as recorded.
