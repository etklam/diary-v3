# [107] Give the AI reports page honest denied, empty and first-run states

Status: needs-triage
Execution: todo
Published: 2026-10-06

Category: bug
Type: Design follow-up
User stories covered: AI Reports V1 — manually requested private review reports with access grants and quotas.

## Observation

Found during the [whole-app page score](../../../docs/design/ui-page-score-2026-10-06.md),
where `/reviews/ai-reports` scored **50/100**.

**The page contradicts itself when access is denied.** `routes/ai-reports.tsx:630`:

```jsx
{!selectedId ? <div className="empty-state"><p>{c.reportNone}</p></div>
```

`reportNone` is "Select a report from the history, or generate a new one." It renders
whenever `!selectedId`, with **no check on `listDenied`** — unlike the history column at
`:613`, which does gate on it. An account without an AI grant therefore sees, side by
side:

- left: "Your account does not have access to this AI action."
- right: "Select a report from the history, or generate a new one."

There is no generate control anywhere on the page, because access is denied. The page
invites an action that does not exist and that the user is not permitted to take.

**Both columns are empty wells, so the two-column scaffold shows through with nothing in
it.** A 320px column holding one sentence beside a 770px column holding another, under a
"History" heading with no history.

**There is no first-run state distinct from the denied state.** A granted user with zero
reports lands on `historyEmpty` on the left and the same `reportNone` on the right — so
the invitation to "generate a new one" is correct for them but they have no more guidance
than the denied user does. The three states that need to look different (denied, granted
but empty, granted with reports) currently collapse into two near-identical layouts.

For context, `/admin/research` in the same review scored 76 largely on the strength of its
empty state — "No research runs yet." plus an explanation of the precondition plus a
"Prepare the first run" action. That is the standard this page should meet.

The page's lede copy is good and should be preserved: "Private review reports you trigger
yourself. Pick a period, check the local data scope, agree once per data recipient, then
generate. Nothing is ever generated on its own."

## Requested outcome

Three visibly distinct states. A denied account is told it has no access and what to do
about it, with no action it cannot take. A granted account with no reports is told how to
make the first one. A granted account with reports gets the current working layout.

## Implementation plan

**1. Guard `reportNone` on access.** `:630` gains the same `listDenied` condition the
history column already uses. This alone removes the contradiction and is a one-line fix.

**2. Design the denied state as one region, not two wells.** When access is denied there
is no history to list and no report to select, so the two-column scaffold should collapse
to a single statement: what the state is, why, and the next step — which is "ask an
administrator for a grant", a human action, so it should say so rather than offering a
control.

**3. Design the granted-but-empty state.** Follow the `/admin/research` pattern: name the
state, state the precondition (period selection, data-scope check, one-time consent per
data recipient), and give it one filled action that starts the flow.

**4. Keep consent and quota legible in all three states.** Consent is per data recipient
and quota is per month; a user who is granted but out of quota is a fourth state and
should not be mistaken for the denied one.

**Verification:** `tests/e2e/ai-reports-worker.spec.ts` and any AI-report page coverage
are updated and must pass, with added cases for **denied**, **granted-and-empty**, and
**granted-and-out-of-quota**. The denied case asserts that no generate control is present
and that no copy invites generation — that assertion is the regression guard for the
actual defect, and it should be mutation-checked by reverting the `:630` guard.

## Provisional acceptance criteria

- [ ] A denied account sees no copy inviting it to generate a report, and no generate control.
- [ ] Denied, granted-and-empty, granted-and-out-of-quota, and granted-with-reports are four visibly distinct states.
- [ ] The denied state names the next step as a human action rather than offering a control the account cannot use.
- [ ] The granted-and-empty state names the precondition and carries exactly one filled action.
- [ ] Neither the denied nor the empty state renders two empty wells side by side.
- [ ] Consent scope and remaining quota are legible wherever they apply.
- [ ] The lede copy about nothing being generated automatically is preserved verbatim in all three locales.
- [ ] Report content, snapshot immutability, cancellation and regeneration behaviour are unchanged.
- [ ] Each new state is covered by a test, and the `:630` guard is mutation-checked.
- [ ] Verified in all three locales, light and dark, at 390/768/1440.
