# [119] The attention list discards its own priority order

Status: accepted
Execution: done 2026-10-15
Published: 2026-10-15

Category: enhancement
Type: Design follow-up
User stories covered: Diary review — seeing what needs attention on the workspace.

## Observation

`portfolio-attention.tsx:11` describes its own contract as *"Up to 50 items, ordered by
priority"*, and the API returns them that way. **The rendering throws that information
away.**

Every item is the same `<li>` (`portfolio-attention.tsx:30`): a `<strong>` reason, a
`<span>` subject, an optional figure, an optional time, and a trailing `Open` link. On a
seeded Overview at 1440 this produces five rows of identical weight:

| Reason | Subject | Trailing link |
|---|---|---|
| Overdue · Diary | Opened a starter position in SYN (due Jul 15) | `Open` |
| Position concentration | SYN 75.76% | `Open` |
| Missing thesis | AAPL | `Open` |
| Missing thesis | MSFT | `Open` |
| Missing thesis | SYN | `Open` |

Three problems, in order of cost:

1. **An overdue review and a missing thesis look the same.** The only expression of
   priority is row order, which is invisible to a reader who is scanning and invisible to
   a screen reader reading linearly. The data knows; the page does not say.
2. **`Open` names nothing and is ~1,150px from its own label.** Five identical links to
   five different destinations, each at the far right of a 1,160px region. The eye travels
   the full width to reach a word that does not say what it will open.
3. **Three rows are the same kind.** "Missing thesis" × AAPL, MSFT, SYN occupies three
   fifths of the region to carry one fact with three subjects.

## Requested outcome

A region where the most urgent item is the most prominent thing in it, where every action
names its object, and where same-kind items do not crowd out different-kind ones.

## Implementation plan

**1. Make the row the link; delete the trailing `Open`.** The whole `<li>` becomes the
target, which fixes the travel distance and the unnamed action at once. The accessible
name should be the reason plus the subject ("Overdue diary — Opened a starter position in
SYN"), not "Open".

**2. Encode severity without introducing colour.** `DESIGN.md` bans the warm-tint slab and
the system is deliberately low-chroma, so the carrier should be structural: rule weight at
the row's leading edge (`--rule-strong` for overdue, `--rule` for the rest), or the reason
label taking the semibold weight only when it is overdue. Pick one and apply it to the
three severity bands the API already distinguishes. Do **not** reach for `--negative` as a
background; the page has no other red and the item is a prompt, not an error.

**3. Group same-kind items.** Collapse runs of one reason into a single row with a count
and the subjects inline ("Missing thesis — AAPL, MSFT, SYN"), linking to the filtered list
rather than to one of the three. Keep the ungrouped form when a run is length 1.

**4. Decide the cap that is actually shown.** The contract allows 50; the region should
show a small number and name the remainder ("and 12 more"), because a 50-row list on the
workspace is a second page, not an attention region.

**Verification:** `overview.spec.ts` must pass. Add a case that seeds one overdue and three
same-kind items and asserts: the overdue row is first and carries the stronger treatment,
the three same-kind items render as one row with a count, each row's accessible name
contains its subject, and no element with the accessible name "Open" remains in the region.

## Provisional acceptance criteria

- [x] Severity is visible without reading order, and is carried by structure rather than a tint or a fill.
- [x] No row's action is named "Open"; every target's accessible name contains its subject.
- [x] Runs of the same reason render as one row with a count; a run of one is unchanged.
- [x] The region shows a bounded number of rows and names the remainder.
- [x] The empty state (`'No items need attention under these rules.'`) is unchanged.
- [x] Verified at 390/768/1440 in all three locales, in light and dark.

## Execution record — 2026-10-15

**There are two attention regions, and the ticket described both while naming one.** The
code references are `portfolio-attention.tsx` (the `/stocks` region) but the measurement —
five identical rows on a seeded Overview at 1440 — is `WorkspaceAttentionSection` in
`overview.tsx`, which merges attention items with the review queue and renders its own
rows. Both had the same defect and both are fixed. What they share now lives in
`attention-display.ts`: the band, the run grouping, and the bound.

**Ruling 1 — severity is the leading rule's weight, and also a word.** The ticket offered
rule weight or label weight and said to pick one; rule weight is the pick, at 3px
`--rule-strong` / 2px / 1px `--rule`, no colour anywhere. But picking a *visual* carrier
only fixes half of what the ticket itself identified: it says row order is "invisible to a
screen reader reading linearly", and a rule weight is equally invisible there. Each row
also carries the band as a visually hidden word at its head — Urgent / Time-bound /
Standing, in all three locales. The visual and the spoken carrier agree.

**Ruling 2 — the two priority scales are different and both are read from their source.**
`ATTENTION_PRIORITY` runs 500→100 with higher meaning more urgent; the Overview's own
table renumbers the merged set 1→7 with lower meaning more urgent. Rather than pick one
and convert, `attention-display.ts` exposes `bandFromContractPriority` and
`bandFromOverviewPriority`, each documented against its own scale, each unit-tested against
the real constant rather than a copy of it.

**Ruling 3 — a grouped row is not one link.** Step 3 asked for the group to link "to the
filtered list". There is no filtered list: no route renders "every holding missing a
thesis", and inventing one to satisfy a rendering would be a route nobody asked for and a
page nobody maintains. The grouped row names the count and then carries **one link per
subject**, each with an accessible name of `<reason> — <subject>`. That satisfies the
acceptance criterion the step existed to serve — every target names its object — without
the new route.

**Ruling 4 — grouping is only of consecutive runs.** Merging every item of one reason
wherever it appears would reorder the region to suit its own rendering, and the order is
the information this ticket exists to preserve. A reason that reappears further down the
priority order stays where the API put it. Pinned by a unit test.

**The cap is five runs, and the remainder is counted in items, not runs** — "and 7 more"
after five rows means seven things, which is what a reader needs to know.

**Verification.** `tests/unit/attention-display.test.ts`, 8 cases, including that the
bands are read from `ATTENTION_PRIORITY` itself. `portfolio-attention.spec.ts` gained the
case the ticket specified — one overdue item first with a measurably heavier leading rule,
three same-kind items as one row with a count and three named targets, nothing in the
region named "Open", every link's name longer than "Open", and the band present in the
reading order. `portfolio-attention` 3/3, `overview` 4/4, `daily-workspace` 4/4,
`portfolio` 4/4. `daily-workspace`'s "many reminders stay bounded" case changed meaning
and says so: seven same-kind reminders are now one row carrying seven named targets rather
than five rows crowding out every other kind, which is the behaviour the ticket asked for.

**Carried in from [121](121-figure-caveat-mechanism.md).** That ticket noted
`portfolio-attention.tsx`'s `hint` ended with the shared coverage constraint written a
fifth way. The hint is now "Ordered by priority." and the constraint is the shared
`*` note at the foot of this region, marked on the concentration figure it qualifies.
