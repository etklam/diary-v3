# [101] Normalize money, quantity, percentage and date rendering across the workspace

Status: needs-triage
Execution: todo
Published: 2026-10-06

Category: bug
Type: Cross-cutting visual bug
User stories covered: Cross-cutting financial display consistency. Portfolio, Company research, Diary reading and review, Timeline, Trade plans.

## Observation

Found during the [whole-app page score](../../../docs/design/ui-page-score-2026-10-06.md).
This is the single most visible defect in the product: **the same number renders
differently on every page that shows it.**

The API stores and returns unnormalised decimal strings. A `POST /api/trade-plans` with
`entryPrice: '182.40'`, `stopLoss: '164.00'`, `targetPrice: '215.00'`,
`maxPositionSize: '4400.00'` came back as:

```json
{"entryPrice":"182.4","stopLoss":"164","targetPrice":"215","maxPositionSize":"4400"}
```

Each page then renders that string its own way. For one seeded AAPL purchase at 182.40:

| Surface | Renders as |
|---|---|
| `/diaries/:id` — Price per share | `182.4` |
| `/diaries/:id/review` — Recorded transactions | `24.0000 × 182.4000` |
| `/stocks` — Average cost | `182.4` |
| `/stocks` — Total cost / Priced cost basis | `2918.4` / `3,892.4` |
| `/stocks/:symbol` — Average cost | `182.4` |
| `/timeline` — trade row | `at 182.4` |
| `/trade-plans` — Target price | `215` |

Two separate conventions collide inside one page on `/stocks`: `2918.4` has no thousands
separator while `3,892.4` does, and `Stale quote · 9/4/26, 3:00 PM UTC` in the table sits
four lines above `Oldest quote: Sep 4, 2026, 3:00 PM UTC` — the same instant in two date
formats.

`/stocks/:symbol` additionally prints six decimal places on figures the reader is meant
to judge: `Portfolio share · cost basis 74.976878%`, `Change +10.000000`, `Change percent
+10.000000%`.

`DESIGN.md` states under Content and i18n that "amounts stay as string inputs and are
stored to two decimals". That is not what ships, so either the statement or the behaviour
is wrong — this ticket treats the statement as the intent and the behaviour as the defect.

**This is a presentation defect, not a calculation defect.** No stored value, projection
or sum is wrong; `formatMarketValue` already handles signed market values correctly
(`+`/`−` preserved, `—` for unknown, true U+2212). The gap is that non-market figures —
prices, quantities, costs, cost bases, portfolio shares — have no shared formatter at
all, so each call site improvises with `toLocaleString`, raw string interpolation, or
`toFixed(4)`.

## Requested outcome

One shared formatting boundary for every figure the user is asked to judge, applied
across the workspace, so the same value reads the same way everywhere. Preserve exact
decimal strings from API projections — this is about *display*, and no rounding may
change a stored value or a computed total.

## Implementation plan

**1. Extend the display layer rather than adding a second one.**
`apps/web/app/market-display.ts` already owns signed market values. Add sibling
formatters there for the unsigned cases: price, quantity, money total, and percentage.
Each takes the API's decimal string, not a `number`, so precision is never lost on the
way in.

**2. Decide the conventions once and record them in DESIGN.md.** Proposed, for triage:
- **Price and cost**: two decimals, thousands separators, locale-aware.
- **Quantity**: up to 4 decimals (the editor already states "Use up to 4 decimal
  places"), trailing zeros trimmed — `24`, not `24.0000`.
- **Percentage**: two decimals maximum. `74.98%`, never `74.976878%`.
- **Instants**: one format per role — a date-only value, a date-and-time value, and a
  relative/stale marker — and the same role renders identically on every page.

**3. Replace the call sites.** At minimum: `/stocks` (holdings table and Portfolio
valuation), `/stocks/:symbol` (position, quote, portfolio share), `/diaries/:id`
(transactions), `/diaries/:id/review` (recorded transactions, currently `toFixed`-style
4dp), `/timeline` (trade rows), `/trade-plans` and `/trade-plans/:id`, and Overview's
portfolio context.

**4. Apply the Figure Rule at the same time.** The same call sites are where
[102](102-confirmed-markup-defects.md) fixes the missing monospace cut; doing both in one
pass avoids touching the markup twice. Ticket 102 owns the CSS, this ticket owns the
value.

**Verification:** a unit suite over the new formatters covering trailing zeros, thousands
separators, 4-decimal quantities, percentage clamping, and the `—` unknown case in all
three locales. Then assert in e2e that the same seeded transaction renders the identical
price string on `/diaries/:id`, `/diaries/:id/review`, `/stocks` and `/timeline` — that
assertion is the actual regression guard, because it is the property that broke.

## Provisional acceptance criteria

- [ ] One module owns price, quantity, money, percentage and instant formatting for the Web app; no page formats a judged figure inline.
- [ ] The same seeded transaction's price renders byte-identically on `/diaries/:id`, `/diaries/:id/review`, `/stocks`, `/stocks/:symbol`, `/timeline` and `/trade-plans`, asserted by a test.
- [ ] Thousands separators are either present or absent consistently within a page and across pages; `2918.4` beside `3,892.4` cannot recur.
- [ ] No percentage renders more than two decimal places; `74.976878%` and `+10.000000%` are gone.
- [ ] Quantities render without padded trailing zeros; `24.0000` is gone.
- [ ] One instant format per role; `/stocks` does not show `9/4/26` and `Sep 4, 2026` for the same value.
- [ ] Exact decimal strings from API projections are preserved in the data layer; no displayed rounding changes a stored value, a sum, or a market-colour classification.
- [ ] `formatMarketValue` behaviour is unchanged: signs on every market value, `—` for unknown, never `0` for missing.
- [ ] DESIGN.md's Data and finance section states the decided conventions, and its "stored to two decimals" claim is corrected to match what ships.
- [ ] Verified in all three locales, light and dark, at 390/768/1440.

## Settled during triage

Nothing yet. The conventions in step 2 are proposals and need a ruling — in particular
whether thousands separators belong on a 4-digit cost basis, and whether the API should
normalise to two decimals at write time instead of (or as well as) the Web app
normalising at read time. The server-side option is out of this ticket's scope as written;
if triage prefers it, this ticket should be split.
