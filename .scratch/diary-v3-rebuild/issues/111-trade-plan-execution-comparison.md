# [111] Fix the trade plan execution comparison region

Status: needs-triage
Execution: todo
Published: 2026-10-06

Category: bug
Type: Design follow-up
User stories covered: Trade plans — compare the recorded plan with what was actually executed.

## Observation

Found during the [whole-app page score](../../../docs/design/ui-page-score-2026-10-06.md),
where `/trade-plans/:id` scored **68/100**. The defects are confined to the execution
comparison region at the bottom of the page; the plan form itself is sound.

**Important scoping note.** The review's first pass recorded two defects on this page that
turned out not to exist — "Target price" and "Maximum position size" appearing as labels
with no inputs, and the Save footer appearing between the Prices and Decision-context
sections. DOM measurement showed all six price inputs render at 44px with their values,
and source order at `routes/trade-plan.tsx:594-601` puts `<footer className="plan-actions">`
last inside the `<form>`, after the context fieldset. Both were full-page screenshot
stitching artifacts on a 2,392px page. **Neither is in scope and neither should be
"fixed".** They are recorded here so the next reader does not rediscover them from the
same capture.

What is real:

**Five identical bordered tiles, all reading "Unavailable".** `trade-plan.css:309` sets
`.execution-values { grid-template-columns: repeat(5, minmax(0, 1fr)) }`, so Buy quantity,
Average execution price, Entry price difference, Entry price difference (%) and Entry zone
render as five equal boxes. Before any transaction is selected every one of them says
"Unavailable". This is simultaneously the identical-card-grid pattern and a five-wide stat
row, against a `DESIGN.md` rule that calls four side by side "the hero-metric template,
not a design" and asks for `.ledger` instead. Five empty boxes is also simply a poor empty
state: it occupies the space of data to communicate the absence of data.

**"Baseline not confirmed" reads as a disabled button.** It renders as a filled lavender
pill immediately left of the "Confirm current plan" button, at similar size and shape.
It is a status, not a control, and it is the only thing distinguishing a confirmed
baseline from an unconfirmed one.

**Two save scopes with no visual separation.** The plan form's "Save trade plan" and the
execution region's "Save execution selection" are different commits on one page. The
second is a disabled filled button in its resting state, which
[102](102-confirmed-markup-defects.md) item 6 covers as a cross-cutting convention
question.

**Figures are unformatted** — `Entry price 182.4`, `Stop loss 164`, `Target price 215` —
because the API returns unnormalised strings. Owned by
[101](101-figure-formatting-consistency.md).

## Requested outcome

Make the execution comparison legible before a transaction is selected and after, replace
the five-tile grid with the ledger idiom, and distinguish baseline status from the control
that changes it. Preserve the manual transaction selection model, the baseline/revision
history, and the stated exclusions (fees, FX, corporate actions).

## Implementation plan

**1. Replace `.execution-values` with a ledger.** Five labelled figures in a column with
right-aligned monospace values and a hairline between rows — the idiom the system already
defines for exactly this. Differences can close the column with the heavier
`.ledger-row-total` rule, which is the accounting convention the system already uses for
position sizing.

**2. Give the pre-selection state a real empty state.** Before a transaction is chosen,
the region should say what to do (`.empty-state` naming the next action) rather than
rendering five boxes of "Unavailable". After selection, any individually unavailable
figure stays labelled as such — `DESIGN.md` requires missing values to be labelled in
text and never shown as `0`, and that must not regress.

**3. Make baseline status a status.** Not a pill that looks like a disabled button.
Whatever treatment is chosen must distinguish confirmed from unconfirmed without relying
on colour alone.

**4. Separate the two save scopes.** The execution region is a distinct commit; it should
read as its own region rather than as more of the plan form.

**5. Let 101 and 102 own the figures and the disabled-button convention.** Do not
re-decide either here.

**Verification:** `tests/e2e/trade-plans.spec.ts` is updated and must pass, with cases for
no-selection, selection-with-complete-data, and selection-with-some-values-unavailable.
The [2026-10-02 changelog](../../../docs/design/CHANGELOG.md) records pre-existing
`trade-plans` failures confirmed against an unmodified tree; characterise those before
starting so this work is not blamed for them.
