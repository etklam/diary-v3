# [130] Give the three locales a compile-time parity check

Status: ready-for-agent

User stories covered: None — engineering quality; no user story, though every localized surface depends on it.

## Observation

The product ships in three locales — `zh-TW` (default), `zh-CN` and `en` — and the copy
lives in per-surface objects. There are **105 files under `apps/web/app` containing `zh-TW`**,
each shaped like `diary-copy.ts` and `quick-copy.ts`:

```ts
export const diaryCopy = {
  'zh-TW': { moreRegions: '這篇日記的其他部分', /* … */ },
  'zh-CN': { moreRegions: '这篇日记的其他部分', /* … */ },
  en:      { moreRegions: 'More about this diary', /* … */ },
};
```

The three objects are hand-kept in sync without a declaration-level parity constraint.
Existing consumers such as `diary-editor.tsx` read `diaryCopy[locale]`: TypeScript infers
a union and rejects an accessed property missing from one locale. Missing keys used by
these consumers therefore already fail typecheck. The remaining gap is exhaustive key-set
parity, including unused keys, extra keys and accesses that narrow to one locale. Browser
assertions check selected phrases, not this complete declaration-level contract.

This is the same class of gap the project already closed elsewhere: figures are guarded by
`figure-formatting-boundary.test.ts`, registers by `check-register-assignment.mjs`, contrast
by `check-design-contrast.mjs`. Locale parity is the largest hand-maintained set in the
codebase and has no guard at all.

## Requested outcome

A missing or extra key in any locale is a type error or a failing check, before it reaches a
browser.

## Implementation plan

**1. Introduce a shared copy type.** Either a small helper — `defineCopy<Keys>()` that
`zh-TW` defines and the other two locales must `satisfies` — or, at minimum, derive a
`type Keys = keyof typeof diaryCopy['zh-TW']` and annotate the other two locales as
`Record<Keys, string>`. Check both missing and extra keys explicitly: a fresh object literal
checked with `satisfies Record<Keys, string>` rejects both, while a helper that accepts
structural subtypes may still allow extras. Preserve existing non-string value shapes,
including functions and arrays, wherever the migrated copy uses them.

**2. Apply it where the payoff is highest first.** Not all 105 files at once: start with the
surfaces a user reads on the main flows (diary, quick, review, portfolio, market, auth,
settings), prove the pattern, then sweep the rest. Record the pattern in `AGENTS.md`'s
conventions so new copy uses it.

**3. Check explicitly defined untranslated placeholders.** Do not fail merely because two
locales share a value: zh-TW and zh-CN legitimately share many phrases, and labels such as
tickers, units and brand names can match English too. Translation quality needs reviewed
copy or a targeted placeholder rule; key-set parity alone cannot establish it.

**4. Consider folding the sweep into a script** (`scripts/check-locale-parity.mjs`) so files
not yet migrated to the shared type are still scanned for key-set mismatch by parsing.

**Verification:** delete a key from the `en` object of a migrated file and confirm `tsc`
fails; add an extra key and confirm either `tsc` or the script flags it; confirm the three
locales render on a spot-checked page in each language.

### Acceptance — 2026-10-25

Two gates, because the 115 copy objects are not all the same shape.

**Compile-time**, for migrated surfaces: `defineCopy` in `apps/web/app/locale-copy.ts`
infers the key set from zh-TW — the default locale — and checks the other two arms against
it as fresh object literals, so a missing key fails as a missing property and an extra key
fails excess-property checking. Non-string values keep their shape: strings, arrays, nested
objects and functions all pass through. Proven to fail both ways:
`TS2741: Property 'moreRegions' is missing` when deleted from `en`, and
`TS2353: Object literal may only specify known properties, and 'inventedKey' does not exist`
when added to zh-CN.

**Static**, for everything else: `scripts/check-locale-parity.mjs` parses with the
TypeScript compiler and compares dotted key paths across the three locales, including nested
objects and array lengths. It checks **114 objects across 196 files** and runs in
`npm run design:check`, so it is in both the pre-merge and deploy workflows. Proven to
fail: removing one key from an unmigrated file's `en` arm reported
`auth-copy.ts › authAsideCopy:10 [missing-key] en is missing: title`.

**It found a real defect on its first run.** `research-studio-copy.ts` had seven keys —
`approve`, `approving`, `handoff`, `handingOff`, `nextAction`, `limitations`,
`noLimitations` — present in `en` and absent from both Chinese locales. Not a blank UI:
`researchCopy` merges `{ ...copy.en, ...copy[locale] }`, so a Chinese reader was being
shown English strings inside a Chinese page. All seven are now translated in zh-TW and zh-CN,
using this file's established vocabulary (`approved: '已批准'`, `handoffComplete: '已建立文章草稿。'`).

Two false-positive classes were eliminated rather than suppressed: objects with an explicit
type annotation are skipped because the compiler already enforces them — which is what makes
`Record<string, Record<'zh-TW' | 'zh-CN', string>>` in `market-policy-copy.ts`, where the
English sentence is the key, a legitimate design rather than a finding — and `as const` is
*not* treated as enforcement, because it controls widening and says nothing about keys.
Step 3 is honoured: a value shared between locales is not a finding, since zh-TW and zh-CN
legitimately share phrases and tickers and units can match English.
`tests/unit/locale-parity.test.ts` (6 tests) pins all of this, including that the check
cannot silently stop finding objects.

**Remaining scope.** Two surfaces (`diary-copy.ts`, `quick-copy.ts`) are migrated to
`defineCopy`; the other ~113 are covered by the script only. The pattern is recorded in
`AGENTS.md` for new copy. Migrating the rest is mechanical and unblocked — it was
deliberately not swept here, as the ticket's step 2 asks.
