# [122] Finish the system at its native edges

Status: accepted
Execution: done 2026-10-15
Published: 2026-10-15

Category: bug
Type: Cross-cutting visual and interaction consistency
User stories covered: Cross-cutting — disclosures and destructive confirmations on every surface.

## Observation

The design system is carefully built where it was built, and stops at the platform
boundary. Three measured instances, in order of reach.

### 1. Twenty-nine of thirty-five disclosures ship the native marker

`apps/web/app` contains **35 `<details>`/`<summary>` pairs**. Only **five selectors**
suppress the platform marker:

```
authoring.css:141   .authoring-section > summary
timeline.css:106    .timeline-filters summary
styles.css:998      .quick-capture-disclosure > summary
styles.css:1110     .nav-more > summary
styles.css:1230     .desktop-preferences-disclosure > summary
```

Everything else renders the OS triangle. **Seven `<details>` carry no class at all** —
`quick-capture-tools.tsx:11` (the "Capture reminder" on the core capture surface),
`buy-transaction-fields.tsx`, `routes/admin-prompts.tsx`, `routes/etf-research.tsx`,
`routes/guru-research.tsx`, `routes/performance.tsx`, `routes/thesis.tsx` — and the
remaining ~22 have a class with no marker rule. The result is a raw `▶` sitting beside
controls that were built to a 44px floor with a focus halo and a tokenised border, and the
open/closed affordance reads differently on nearly every page that has one.

### 2. Thirty-five `window.confirm` calls against one designed dialog

`routes/diary.tsx:159-160` does this properly: a `<dialog className="delete-dialog">` that
names the entry being deleted, autofocuses Cancel, and disables both controls while the
delete is in flight. **It is the exception.** `window.confirm` is called **35 times across
17 files**: `stock-notes.tsx`, `evidence.tsx`, `article-languages.tsx`, `admin-post.tsx`,
`routes/price-alerts.tsx`, `routes/achievements.tsx`, `routes/admin-users.tsx`,
`routes/admin-blog.tsx`, `routes/thesis.tsx`, `routes/partners.tsx`,
`routes/admin-article-translations.tsx`, `routes/diary-review.tsx`, `routes/admin-email.tsx`,
`routes/trade-plan.tsx`, `routes/etf-admin.tsx`, `routes/ai-reports.tsx`,
`routes/api-keys.tsx`.

A native confirm cannot be styled, cannot be translated by the app's own i18n, names the
origin rather than the product, and cannot show the user *what* is about to be deleted. On
a product whose subject is a durable record of decisions, the confirmation step is not a
place to use the browser's dialog.

Two tickets already removed `window.confirm` from their own surfaces
([96](96-discipline-page-redesign.md), [114](114-admin-article-list-rows.md)) without the
pattern being generalised, which is how 35 remain.

### 3. Destructive actions sit before constructive ones

`routes/diary.tsx:159` renders the entry footer as:

```
[Return to <SYM> research]  [Delete diary (danger)]  [Write a diary (secondary)]
```

Delete comes first in reading order on a page that, at 390, is 2,984px long — so the last
thing in the user's path after reading an entry is its delete button. The dialog behind it
is good, which is the only reason this is not higher severity.

## Requested outcome

One disclosure component and one confirmation component, used everywhere, with destructive
actions placed where they are not the default target.

## Implementation plan

**1. One `<Disclosure>` component in `ui.tsx`.** It owns the marker suppression, the
marker itself, the 44px target, the focus treatment and the open/closed transition, and
takes a variant for the two shapes already in use (the icon-button form in
`.quick-capture-disclosure`, the inline-heading form in `.authoring-section`). Replace all
35 call sites. Where a page's existing class carries layout as well as marker rules, keep
the layout class on the element and move only the summary treatment into the component.

**2. One `<ConfirmDialog>` component**, modelled on `routes/diary.tsx`'s delete dialog —
it is already the right shape. It must name the object, route its copy through the existing
i18n, autofocus the non-destructive choice, disable both controls in flight, close on
`Escape`, and return focus to the trigger. Replace all 35 `window.confirm` calls. Audit
whether each one should confirm at all: several guard an unsaved draft, which is a
different interaction from deleting a record and may want a different answer.

**3. Move destructive actions out of the primary action row.** On `/diaries/:id` the
footer should offer the constructive next step; Delete belongs in the entry's own overflow,
near the record it destroys rather than at the end of the page. Apply the same reading to
the other surfaces touched by step 2.

**4. Record the rule in `DESIGN.md`** beside the existing Buttons rule, so the next surface
does not re-derive it. `DESIGN.md` has a disclosure recipe for layout and no rule about the
marker, which is why this drifted.

**Verification:** `tsc --noEmit` and `eslint` clean. Playwright cannot assert on a native
`confirm`, so the current coverage of those 35 paths is thin by construction — adding the
dialog makes them testable, and each replaced call site should gain an assertion that the
dialog appears, names the object, and that Cancel leaves state unchanged. Add a static
check that `window.confirm` does not reappear, beside `scripts/check-design-contrast.mjs`.

## Provisional acceptance criteria

## Execution record — 2026-10-15

**The ticket's own warning was the finding.** Its Related work said "Read both before
writing the component so the third attempt is the shared one" — and there already *was* a
second attempt. `authoring-controls.tsx` exported a component literally called
`ConfirmDialog`, built by [96](96-discipline-page-redesign.md) and
[114](114-admin-article-list-rows.md), used on six surfaces. Writing a new one beside it
would have made three. What shipped is **one**: the declarative `ConfirmDialog` is deleted
and its six call sites moved to the new `useConfirm()`, along with the three remaining
hand-rolled `.delete-dialog` instances (`routes/diary.tsx`, `routes/discipline.tsx` ×2,
`discipline-transfer.tsx`, `admin-translation-batch.tsx`) and all 32 `window.confirm`
calls. The `.delete-dialog` CSS rule is gone; `.confirm-dialog` in `styles.css` replaces it.

**Ruling 1 — imperative, not declarative.** The existing component took `open` plus
`onConfirm`/`onCancel`, which forces every caller to carry a `doomed`/`confirming` state
field and split one decision across three places. `useConfirm()` returns an `await`-able
function, so `if (!window.confirm(x)) return` becomes
`if (!await confirm({...})) return` — the call site keeps the shape it already had. That
is what made 32 conversions tractable rather than 32 rewrites. The richer form is still
there: passing `action` runs the work with the dialog open and both controls disabled,
which is what `routes/diary.tsx`'s dialog did and the reason it was the stated model.

**Ruling 2 — `<details>` stays; only the marker is ours.** Replacing the element with a
button-plus-region would have cost the browser keyboard model DESIGN.md explicitly
prefers. `Disclosure`/`DisclosureSummary` wrap the native pair and own marker suppression,
the `icons.tsx` chevron, the target height and the rotation; a page keeps its own class on
the element, so every bespoke layout rule (`.nav-more`, `.authoring-section`,
`.timeline-filters`, `.quick-capture-disclosure`, `.desktop-preferences-disclosure`) still
outranks the shared treatment and nothing moved. All 37 call sites converted; the ten that
drew their own chevron dropped it.

**Ruling 3 — the confirmation audit changed two call sites, not the eighteen.** Step 2
asked whether each guard should confirm at all, noting several guard an unsaved draft. They
should: a draft guard is a real question with a real cost, and the shipped form separates
the two kinds by tone — `tone: 'danger'` for anything that destroys a record, plain for a
reversible choice, with one shared affirmative label (`t('discard')`) so eighteen surfaces
stop each inventing their own. What did change: `/diaries/:id`'s delete left the footer
entirely (ruling 4), and `/admin/blog`'s two deletions now ask separately, which is
[114](114-admin-article-list-rows.md)'s finding applied at the call site rather than in the
shared helper that hid it.

**Ruling 4 — delete moved up, not into an overflow.** Step 3 proposed an overflow menu;
there is no overflow idiom in this system and [106](106-watchlist-row-controls.md)
deliberately removed the one attempt at one. Delete now sits beside Edit in the entry's own
title row — with the record it destroys, as the step asked — at `.button-compact` height so
it reads as the quieter of the two. The footer carries only the next thing to do. The
previous arrangement was worse than the ticket described: with no company to return to
(the common case) Delete was the **first** control in that row, not the middle one.

**The check is `scripts/check-native-edges.mjs`**, wired into `npm run design:check`
beside the contrast and figure-rule checks. It fails on a raw `<details>`/`<summary>`
outside `ui.tsx` and on any `window.confirm`, and reports what to use instead.

**Verification.** `tsc --noEmit`, `eslint`, `design:check` (3/3) and 1190 unit tests pass.
**The e2e suite was the real work here, and the ticket predicted why**: "Playwright cannot
assert on a native `confirm`, so the current coverage of those 35 paths is thin by
construction." 17 specs drove the native dialog through `page.on('dialog')` handlers that
could only accept or dismiss, and asserted nothing about what was asked. All are converted
to the new `acceptConfirmation`/`cancelConfirmation`/`confirmation` helpers in
`tests/support/e2e.ts`, and seven of them now **assert the object by name** — the
achievement, the key label, the ETF symbol, the note title, the account email, the trade
plan symbol — which was not previously expressible. 134 cases green across `achievements`,
`admin-users`, `admin-blog`, `admin-ai`, `ai-reports-worker`, `api-keys`, `diary-review`,
`discipline`, `email-account-lifecycle`, `etf-admin`, `evidence`, `partners`,
`partner-timeline-parity`, `quick-authoring-follow-up`, `stock-notes`,
`stock-note-sharing`, `thesis`, `trade-plans`, `timeline`, `diary-list`, `holdings`,
`company-hub`, `posts` and the authoring suites.

**One class of native dialog stays native.** `beforeunload` is the browser's and cannot be
replaced; `diary-editor.spec.ts`, `ledger-corrections.spec.ts` and
`research-diary-handoff.spec.ts` still drive it through `page.on('dialog')`, correctly.
