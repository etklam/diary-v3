# [137] Every account defaults to Asia/Taipei silently, and the capture date changes under the author

User stories covered: 07 (preferences and timezone), 09 (Quick Diary capture), 02 (first

## Observation

`packages/db/src/schema/account.ts:47`:

```
timezone: varchar('timezone', { length: 50 }).default('Asia/Taipei').notNull(),
```

Nothing in registration asks, states, or confirms it. `/settings` has the correct control —
common options plus an explicit use-device-timezone action — but a reader has to already
know it matters to go looking.

For this product that is not a preference. `PRODUCT.md` describes the product as a dated
record of judgments, `DESIGN.md` makes the ISO calendar day the one format that is identical
in every locale, and `formatDay` prints it unlocalized precisely because "a dated record
sorts and aligns on ISO". The account timezone decides which day a judgment is filed under.
A reader in New York or London files their first weeks of entries under a day that is not
theirs, in a record whose whole value is being able to go back to a specific day.

**The capture surface then changes the date in front of them.** `quick-composer.tsx:190`
seeds the field from the device:

```
const deviceDate = initialDate ?? calendarDateInTimezone(new Date(), Intl.DateTimeFormat().resolvedOptions().timeZone)
```

and `:672` overwrites it once `/api/auth/me` resolves:

```
// The account timezone is authoritative for today's date, but never overrides a
// date the author chose or one carried in from a capture link.
useEffect(() => {
  if (!accountDate || initialDate || dateTouched.current) return
  setForm(current => (current.date === accountDate ? current : { ...current, date: accountDate }))
}, [accountDate, initialDate])
```

The comment is accurate and the guards are correct — it respects a touched field and a
capture link. But for the untouched default case it means a reader at 21:00 in New York
watches the date field move from the 29th to the 30th part-way through composing, with no
notice. The rule being applied is right; it is simply never stated.

**The one timezone the forms do state is the other one.** `diary-editor.tsx:1286` renders
"Times below use your device timezone: …" (`diary-copy.ts:6`). That sentence is true and
scoped to the transaction and review instants in the sections below it — it is not about the
diary's calendar day, which comes from the account. Two timezones are in play in one form
and the one that decides the filing day is the unstated one.

## Requested outcome

A new account confirms its timezone before its first entries are filed, and no capture
surface silently rewrites a date the reader is looking at.

## Implementation plan

**1. Ask once, at the moment it is first true.** The first-use block on Overview
(`overview.tsx:824`, `FirstUseSection`) is the right place: it renders exactly once per
account, before any entry exists, and it already owns the "here is how to start" moment. Add
one line stating the account timezone and, when
`Intl.DateTimeFormat().resolvedOptions().timeZone` differs from it, one secondary action that
sets the account to the device zone through the settings endpoint that already exists.

Do **not** add a registration step. `registration-complete.tsx` is the last screen of a
verification round-trip and `auth-form.tsx` is a two-field form; both are deliberately
minimal, and a timezone select there would be a decision asked before the reader knows what
it affects. Stating it where the first entry is about to be written is the cheaper question.

**2. State the account timezone where the date is decided.** Add a permanently visible note
on the quick composer's destination row naming the zone the day is resolved in — the pattern
`DESIGN.md` already sanctions for constrained figures (`CaveatNote`: permanently visible, no
hover, works on touch). Once the rule is stated, the overwrite stops being silent.

**3. Do not change the overwrite rule itself.** The account timezone *should* be
authoritative; `calendarDateInTimezone` with the account zone is what the API will file
under, and seeding from the device is only a pre-resolution guess. Changing it would create
a worse bug where the field disagrees with the stored row. The fix is disclosure, not
behaviour.

**4. Leave the default where it is.** `Asia/Taipei` is a reasonable default for this
product's audience and changing a column default does not help any account that already
exists. The defect is that it is never surfaced, not that it is wrong.

**Verification:** `npm run lint`, `npm run typecheck`, `npm run test:unit`,
`npm run design:check`, `npm run contracts:check` if the settings call shape is touched (it
should not be — `/settings` already writes this field).

Scope was deliberately held to disclosure. The tempting larger change — detect the device
zone at registration and write it without asking — was rejected: a shared or travelling
device would then silently refile the reader's days, which is the same defect pointed the
other way.

## What was built

**Stated on the first-use block.** `FirstUseTimezone` renders one quiet line naming the
account timezone, and *only* when the device disagrees does it add the device zone and a
single quiet control that writes it. A reader whose device already agrees sees a sentence and
no decision. The write reads `/api/user/settings` and PUTs it back with the timezone
replaced, because that endpoint replaces the whole record; then `refreshViewer()` so the
shell and the date line reflect it without a reload.

**Stated where the date is decided.** A permanently visible note under the quick composer's
destination region names the zone the capture date resolves in — the project's own caveat
idiom: no hover, no `title`, works on touch. The silent overwrite at `quick-composer.tsx` is
unchanged, which was deliberate: the account zone *should* be authoritative, since it is what
the API files under. The defect was that nothing said so.

No registration step was added and the column default was left alone, both as planned.
