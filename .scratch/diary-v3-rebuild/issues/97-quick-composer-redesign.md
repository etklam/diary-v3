# [97] Redesign both diary authoring surfaces as one writing system

Status: accepted
Execution: done
Published: 2026-10-04

Category: enhancement
Type: Design follow-up
User stories covered: US-015, US-016, US-017. Quick Diary capture and full Diary authoring.

Scope covers `/diaries/quick` and the `Cmd/Ctrl+J` capture dialog (`quick-composer.tsx`) **and** `/diaries/new` (`routes/new.tsx`, `diary-editor.tsx`). They are the same domain — one person writing one diary for one date — and are designed as one system here.

## Observation

A design review of the Quick Diary composer — `apps/web/app/quick-composer.tsx`, `quick-fields.tsx`, `quick-entry.tsx`, `apps/web/app/routes/quick.tsx`, `apps/web/app/quick.css`, with the recorded captures in `docs/design/evidence/quick/` — scored 27/40 against Nielsen's heuristics. The deterministic slop detector returned zero findings across all six source files. This surface is in materially better shape than most of the workspace: the uncertain-append recovery is the strongest error-recovery flow in the codebase, and `Cmd/Ctrl+J`, `Cmd/Ctrl+Enter`, templates, snippets, recent tags and voice capture give it real accelerators.

The problems are compositional. One component serves two very different containers (a 760px modal and a full page), and everything that has been added to it over several rounds has been appended to the same single column.

**Reading order still opens on configuration, not writing.** Inside the form (`quick-composer.tsx:73`) the order is `Destination` h2 → date input → save-mode select → `Content` h2 → textarea. [91](91-quick-destination-placement.md) raised exactly this and is ruled here. Both controls are correct by default on nearly every capture: today's date, create. The person arriving to record a thought passes a section heading and two controls before reaching the only field they came for.

**Everything after the textarea is one undifferentiated stack, four levels deep.** `Optional details` is a `<details>` holding the template select, company context, the `QuickFields` fieldset (up to eight further controls plus related trades), apply/regenerate buttons, the title input, the tags textarea, the recent-tags fieldset, and a nested `<details>` for snippets — which in turn holds a `Manage snippets` toggle revealing a fourth-level sub-form with its own select, name, body, save and delete. Nothing marks which of these a person actually needs.

**Choosing a template silently rewrites the writing area that is scrolled out of view.** The template `<select>` lives inside `Optional details`; the `suggested` effect (`quick-composer.tsx:54`) replaces untouched title and content. The cause is below the fold and the effect is above it, with no announcement.

**The two biggest controls on the page are Preview Markdown and Start voice input.** They sit immediately under the textarea as full-size secondary buttons (`quick-composer.tsx:73`), so at 390px they are the most prominent interactive elements after the writing area, ahead of save. Preview also swaps the textarea in place and relabels its own trigger to "Content", which is a poor name for "go back to editing". [94](94-quick-diary-button-consistency.md) covers their sizing; this ticket covers their placement and weight.

**The desktop page ignores its width.** `/diaries/quick` renders the composer inside `section.editor` as one narrow column; at 1440 the right half of the workspace is empty while optional fields are hidden behind a disclosure that could simply be visible. The modal is correct as a single column; the page is not. This is the Quick Diary instance of [93](93-desktop-workspace-space-utilization.md).

**Three native `window.confirm` calls.** Discarding unsaved changes (`quick-composer.tsx:51`), replacing writing with a snippet (`insert(true)`, `:63`), and regenerating from a template (`:73`). The project ships a dialog pattern; these are unstyled, untranslatable through the normal path, and inconsistent with it.

**Defect: a sentence is used as a CSS class name.** `quick-composer.tsx:73` renders `<p role="status" className={draftError?'error':savedDraft?c.draft:''}>`. When a draft saves, `className` becomes the copy string — `"草稿已儲存在此裝置，保留 24 小時。"` in zh-TW. It is visually harmless today because no such class exists, but it is wrong and will silently defeat any future styling of that status line. The draft status also sits between the optional details and the submit button, far from the writing it describes.

**Minor.** `submitBlocked` includes `checking`, so immediately after changing the date the save button greys out with no stated reason (the lock itself is deliberate and must stay — see Out of scope). The reflection template exposes `Rating (0–5)` as a number spinner. `.quick-writing .sr-only` re-declares the global utility from `styles.css:482`. Spacing is managed by blanket overrides that then need counter-overrides (`.quick-composer label { margin-bottom: var(--space-5) }` plus `.quick-composer button + label { margin-top: var(--space-5) }` plus `.quick-composer .actions { margin-bottom: var(--space-5) }`). The saved state offers four equally weighted actions at the one moment the flow should feel finished.

## The full editor, `/diaries/new`

Added to scope 2026-10-04: the two authoring paths write the same object and must read as one system. The full editor fails in the mirror image of the composer — where Quick hides everything behind a disclosure, the editor hides nothing.

**Eight sections of equal weight, all expanded, in one column.** Diary date, Title, Company context, Content, Tags, Reasoning at the time (thesis, risk, execution), Transactions, Review diary, Diary reminders — each a heading with a rule, each the same weight, none deferred. Neither surface practises progressive disclosure; they sit at opposite extremes of the same axis.

**The writing field is the narrowest field on the page.** `.editor` caps the column at 880px (`styles.css:1412`) while `.editor-content` caps the textarea at `72ch` (`diary-editor.css:31`). Title, company context, thesis, risk and execution take the full 880px, so the field that matters most ends roughly 100px short of every field around it and the column has a ragged right edge. The 72ch measure is correct per DESIGN.md; applying it to one field instead of the form is not.

**Two placements for the same control.** `Preview Markdown` sits above the Content label, right-aligned and detached from the field it previews. In the composer it sits below the textarea. Same control, same purpose, two positions.

**Two models for tags.** The editor renders one labelled input per tag plus a `Remove tag` button and a full-width `Add tag` button — ten tags cost twenty controls and ten labels (`diary-editor.tsx:114`, `:131`). The composer uses a single newline-delimited textarea (`quick-composer.tsx:66`). Same field, same contract, two unrelated interaction models, and only one of them has the comma defect recorded below.

**The same timezone fact, three times, three phrasings.** `Asia/Taipei` under Transactions, `Optional. Uses your device timezone: Asia/Taipei` under Review diary, `Choose times in your device timezone: Asia/Taipei` under Diary reminders.

**Date first again.** The editor opens on Diary date exactly as the composer opens on Destination, so both paths put a correct-by-default control ahead of the writing.

**The desktop page uses roughly 670 of 1440px.** The same finding the user reported in [93](93-desktop-workspace-space-utilization.md), on the route that is its clearest case.

## Requested outcome

Make the two authoring paths one writing system: the writing area first and largest on both, the same control in the same place with the same weight on both, one tag model, one measure, and desktop layouts that use the width each container actually has. Preserve every existing capability on both paths, all keyboard accelerators, both draft lifecycles, the revision and same-date conflict handling in the editor, and the entire uncertain-append state machine in the composer.

## Implementation plan

**Delivered as one change set across both surfaces, in this order. Ruled 2026-10-04: this ticket is not split into a composer slice and an editor slice.** Step 9's shared controls are what make the two paths consistent, so splitting would mean building each control twice and reconciling them afterwards.

**1. Write first — ruled 2026-10-04, no longer blocked.**
- Reorder the form: writing area first; destination second, rendered as one quiet summary line — date, create/append, and the existing-diary note — that expands to the current date input and save-mode `<select>`.
- The `<select>` itself stays, the by-date lookup stays, and the submit lock during lookup stays; this is a placement change only, not a change to the append state machine.
- The existing-diary note stays in the collapsed summary, so an occupied date is still surfaced before the author commits words — the correctness affordance [64](64-quick-content-first.md) was protecting survives the reordering.
- `data-testid="quick-existing-destination"` and `data-testid="quick-existing-title"` survive with their current meaning; `.quick-destination` and `.quick-writing` share grid, gap and heading rules in `quick.css` and are untangled as part of this step.
- The ruling and its constraints are recorded in [91](91-quick-destination-placement.md), which stays open as the decision record rather than closing as `wontfix`.

**2. Put the controls that change the writing next to the writing.**
- Move the template chooser above the textarea as a visible four-option control (Free writing / Trading note / Post-market reflection / Market observation), because selecting one rewrites the content.
- Template-specific fields (`QuickFields`) render directly under the writing area when a template is active, not inside the generic optional bucket.
- Apply / Replace-with-template keep their existing confirm semantics but move beside the template chooser.
- Announce template-driven content replacement through the existing status region.

**3. Flatten the disclosure tree to one level.**
- `Optional details` keeps company context, title and tags.
- Snippets become a sibling disclosure at the same level, not a nested one; `Manage snippets` opens the project dialog instead of expanding a fourth level inline.

**4. Attach the writing-area toolbar.**
- Preview and voice capture become compact quiet controls on a toolbar row bound to the textarea, not two full-size secondary buttons stacked below it. Apply [94](94-quick-diary-button-consistency.md)'s sizing ruling here rather than re-deciding it.
- The preview toggle is labelled for what it does on return ("Back to writing"), and preview renders in a bounded region that keeps the editing affordance visible.
- The draft status line moves to the toolbar row, beside the writing it describes.

**5. Give the desktop page a two-column layout.**
- At the agreed desktop breakpoint, `/diaries/quick` places writing plus its toolbar and the submit control in the primary column, and destination, template fields, company context, title and tags in a secondary column — so the optional controls are visible rather than hidden behind a disclosure on a screen that has room for them.
- The `Cmd/Ctrl+J` dialog keeps the single-column stack with the disclosure; the two containers stop being forced into one composition.
- The breakpoint follows [93](93-desktop-workspace-space-utilization.md) if that lands first.

**6. One confirmation language, one defect fix.**
- Replace all three `window.confirm` calls with the project dialog pattern.
- Fix `className={c.draft}` so the status line carries a class name, not a sentence.
- Replace the `Rating (0–5)` spinner with a six-option radio group.
- Remove the local `.quick-writing .sr-only` in favor of the global utility.
- Queue a submit that arrives while the destination lookup is in flight and fire it when the lookup resolves, and state why save is unavailable instead of only greying it. The lock stays; only the swallowed `Cmd/Ctrl+Enter` keystroke is fixed. See Re-evaluated exclusions.
- Split tag entry on newlines, `,`, `，` and `、`, and say so in the field label, so a comma-separated list stops being stored as one tag. See Re-evaluated exclusions.
- Collapse the blanket label/action margin overrides in `quick.css` into layout-owned spacing on the space scale.

**7. Finish the flow.**
- The saved state leads with one filled primary action (Open diary); Edit details, New note and Return to company research become quiet actions. Existing focus behavior is preserved.

**8. Make the full editor the same system.**
- Writing first: content and its toolbar lead the form; date, title and company context follow as the same summary-then-expand pattern step 1 defines for the composer.
- One measure: the 72ch cap governs the writing column rather than the textarea alone, so the form stops ending at two different right edges.
- Progressive disclosure: Reasoning at the time, Transactions, Review diary and Diary reminders become deferred regions rather than nine always-open sections of equal weight. What is open by default is a triage decision; the default should reflect what a person fills on most diaries, not what the data model contains.
- The timezone fact is stated once for the form.
- Desktop two-column, matching step 5: writing and its toolbar in the primary column; date, title, company context, tags and the deferred regions in the secondary column.

**9. Extract what is genuinely shared.**
- One tag control for both paths, replacing the editor's per-tag inputs and the composer's newline textarea, carrying the separator fix from step 6 and the recent-tag chips from [70](70-recent-diary-tags.md).
- One preview control, in the same position relative to the writing area on both paths, with the same label semantics.
- One company-context control (already shared as `CompanyContextInput`) and one date control, presented identically.
- Shared presentation only. The composer's uncertain-append machine and the editor's draft lifecycle and conflict handling stay where they are — see Re-evaluated exclusions.

**Verification:** `tests/e2e/diary-response-loss.spec.ts` must pass unchanged — it guards the uncertain-append machine and is the gate on this work. Quick Diary and full editor E2E coverage is updated for the new control structure on both paths, including the `Cmd/Ctrl+Enter` path, draft restore/discard, template application, the dialog entry point, the shared tag control, and the editor's revision-conflict and reminder flows. Captures in `docs/design/evidence/quick/` and `docs/design/evidence/diary/` are retaken at 1440 and 390 for the page, the dialog and the full editor.

## Re-evaluated exclusions

The capture-cost review recorded in [FOLLOW-UP-ISSUES.md](../FOLLOW-UP-ISSUES.md) ruled five findings not worth filing. They were re-examined against source on 2026-10-04. Three of the five rested on a premise that no longer holds or on a framing that bundled a cheap fix with an expensive one; the cheap halves are pulled into this ticket. Two are upheld.

**Overturned in part — the submit lock during destination lookup.** The original reason was that the benefit only appears on a degraded network. Since that ruling, [84](84-quick-keyboard-submit.md) shipped `Cmd/Ctrl+Enter` (`56e1f8c`). The handler at `quick-composer.tsx:73` calls `event.preventDefault()` and then returns when `submitBlocked` is true, and `submitBlocked` includes `checking`. The lookup runs on mount, so the fastest capture path — type, then `Cmd/Ctrl+Enter` — now hits a keystroke that is swallowed with no feedback at all. The lock itself stays: the create/append decision depends on the lookup result and the correctness argument is sound. What changes is that a submit arriving during the lookup is **queued and fired when the lookup resolves**, and the unavailable state says why. No write semantics change; `tests/e2e/diary-response-loss.spec.ts` is untouched. Added to step 6.

**Reframed — the create/append `<select>` stays, but stops offering an impossible option.** The original reason was that removing it saves one glance. Against source, the asymmetry matters more than the glance: selecting Create when a diary already exists is a guaranteed `409 DIARY_ALREADY_EXISTS` (`apps/api/src/diary-routes.ts:55`), while selecting Append when none exists falls through to an ordinary insert (`apps/api/src/diary.ts:118-160`). One of the four combinations can only fail. The control is not removed — it is annotated, so the failing combination is prevented rather than discovered. Folded into step 1, which already restructures this region.

**Overturned in part — tag entry.** The chip control stays rejected; the eight recent-tag chips from [70](70-recent-diary-tags.md) do cover repeat tagging, and that fix is expensive. But the rejection was attached to the wrong defect. `form.tags.split('\n')` (`quick-composer.tsx:66`, `:69`) splits on newlines only, and the server schema accepts any trimmed 1–100 character string (`packages/contracts/src/index.ts:519`). Typing `growth, china` — the universal habit, and the only habit with a full-width `，` in zh-TW and zh-CN — stores one tag literally named `growth, china`, which is then offered back as a recent-tag suggestion indefinitely. The full editor uses per-tag inputs instead (`diary-editor.tsx:114`), so the two authoring paths disagree on the model. The fix is to split on newlines, `,`, `，` and `、`, and to say so in the label. Added to step 6.

**Upheld, with one split — snippets and recent tags on the server.** Snippets are user-authored content whose only copy is `localStorage`; moving them needs a table, a migration, contracts, endpoints and tests. That cost judgment stands. Recent tags are different in kind: `rememberRecentTags` (`apps/web/app/recent-tags.ts`) only caches the last eight tags already written to diaries the account owns, so a derived list needs one read query and no new storage or write path. The bundle hid that asymmetry. Filed separately as [98](98-recent-tags-from-saved-diaries.md); not part of this ticket.

**Superseded — merging `/diaries/quick` and `/diaries/new`.** The original ruling called this a maintenance argument rather than an input-cost one, and as a *code* argument that still holds: the quick path owns the uncertain-append machine guarded by `tests/e2e/diary-response-loss.spec.ts`, the editor owns the draft lifecycle from [75](75-diary-draft-lifecycle.md) and same-date conflict handling from [65](65-diary-date-conflict.md), and putting both state machines in one component raises risk without reducing input cost.

What that ruling never addressed is the *design* argument the user raised on 2026-10-04: the two paths write the same object for the same person on the same date, so they should read as one system regardless of how many state machines sit behind them. That is now in scope — steps 8 and 9 above — and it is a different claim from merging the implementations. Shared presentation and shared controls do not require shared state.

Whether the two state machines should eventually become one stays open, and is better decided *after* this work: the extraction in step 9 is what reveals how much is genuinely common. Recorded under Open triage decisions rather than settled here.

Also deferred: the cold-start wait ([90](90-quick-cold-start-wait.md)) and share-target entry ([86](86-share-target-into-quick-diary.md)) remain their own tickets.

## Triage decisions — ruled 2026-10-04 during implementation

- **The two-column layout starts at 1100px**, one pixel past the `sidebar-narrow` breakpoint, where the sidebar stops shrinking and the content box can hold a 72ch writing column plus a 280px aside. [93](93-desktop-workspace-space-utilization.md) follows this breakpoint rather than setting its own.
- **The template chooser stays a native `<select>`**, moved above the writing area. Four options do not justify a custom segmented control, and ticket [95](95-dropdown-layout-density.md) just ruled that this system keeps native select behaviour. Free writing stays the default.
- **[94](94-quick-diary-button-consistency.md) was absorbed into step 4**, not run as its own slice: its sizing question only has one answer once the controls are placed, and placing them first avoided deciding the same thing twice.
- **A deferred editor region opens itself when it already holds content** — a diary with transactions opens Transactions, an empty one does not. The rule is the same for a capture-context diary, because the rule reads the data, not the entry point.
- **Merging the two state machines stays open.** The extraction landed as shared presentation only; nothing in it argues for merging the uncertain-append machine with the editor's draft lifecycle.

## Execution record — 2026-10-04

Shared controls live in `apps/web/app/authoring-controls.tsx` and `authoring.css`: `TagField`,
`WritingToolbar`, `ConfirmDialog`, `splitTags`/`joinTags`, and the `.authoring-grid` two-column
layout both paths use. Deviations from the plan, all deliberate:

- **`tests/e2e/diary-response-loss.spec.ts` changed by three lines.** The plan required it to pass
  unchanged *and* required the editor's per-tag inputs to be replaced by one control; those two
  requirements cannot both hold. Every assertion about the write machine is untouched; only the
  three lines that typed two tags through the old per-tag inputs now type them through the shared
  field. The spec passes.
- **The editor's date, title and company context are not collapsed.** Step 8 proposed the
  composer's summary-then-expand pattern here too. They moved into the secondary column and stay
  visible: in the editor the date is a correctness-critical field that several flows (date
  conflict, append, review scheduling) arrive on directly, and hiding it behind a disclosure would
  cost a click on the path the conflict machine already makes hardest.
- **The draft status line sits on the composer's toolbar, but the editor's save status stays in
  its footer.** They are different facts: one describes a device draft beside the writing, the
  other describes the pending save beside the save button.
- **No `authoring-two-column` on the Cmd/Ctrl+J dialog or the `/design-preview` quick editor**, so
  both keep the single-column stack the plan asked for.
