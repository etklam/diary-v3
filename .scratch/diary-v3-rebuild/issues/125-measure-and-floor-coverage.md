## Observation

The suite is large and green — **134 test files / 1198 unit tests** in 16s, plus ~92
integration files and ~90 browser specs — but nothing measures what it touches. There is
no coverage configuration anywhere: `grep -rn "coverage" package.json vitest.config.ts`
returns nothing, and no `@vitest/coverage-*` package is installed.

That leaves the questions the numbers cannot answer:

- Do the security-critical modules carry tests proportional to their risk?
  `apps/api/src/auth-session.ts` (546 lines), `apps/api/src/ledger.ts`,
  `apps/api/src/rate-limit/`, and `packages/domain`'s calculations are where a silent
  regression is most expensive.
- Is coverage rising or falling over time? Without a floor, every future ticket can quietly
  lower it and no reviewer would see it.
- Which branches of the request-authentication middleware (`apps/api/src/app.ts:266-352`),
  CSRF check and body-limit path are actually exercised?

Test *count* is not the metric — an integration test that asserts a 200 can cover a wide
swath with little assertion depth, and a snapshot-style unit test can cover lines without
covering branches. The point of this ticket is not a high global number but a **measured
floor on the few packages where being wrong matters**, and a visible trend.

## Requested outcome

A coverage report that runs in CI, and a branch/line floor on the modules whose failure
would be a security or correctness incident.

## Implementation plan

**1. Add `@vitest/coverage-v8`** and a `test:coverage` script; wire the report into CI as
an artifact. Use the existing `vitest.config.ts` `include`/`exclude` so the generated
client (`packages/api-client/src/generated.ts`) and fixtures do not drown the signal.

**2. Measure first, gate second.** Run once on current `main`, record the baseline per
area, and commit the numbers. Do not invent a threshold before seeing the baseline.

**3. Set floors only where they matter.** Candidate set: `packages/domain/src/**`,
`packages/contracts/src/**`, `apps/api/src/auth-session.ts`, `apps/api/src/ledger.ts`,
`apps/api/src/rate-limit/**`, `apps/api/src/app-context.ts`. A workable shape is a modest
global floor plus higher per-directory thresholds for this set. Pick thresholds a few
points below the measured baseline so ordinary refactoring does not trip them, and raise
them deliberately.

**4. Publish the trend** in the CI job summary so a drop is visible on the pull request that
caused it.

**Verification:** `npm run test:coverage` produces a report; deleting coverage from one
targeted module (a throwaway experiment, not committed) drops it below its floor and fails
the gate.

### Acceptance — 2026-10-25

`@vitest/coverage-v8@5.0.0` added, pinned to the `vitest` version. `npm run test:coverage`
emits text, `json-summary` and HTML; it replaces the bare `test:unit` step in the
pre-merge gate and publishes a trend table to the job summary with the report uploaded as an
artifact.

**Measured before gating, as the ticket required — and the measurement mattered.** The first
draft of this change proposed a 55% line floor; the baseline is 28.5%, so the guess was 26
points above reality. Everything is recorded in
[`docs/audits/coverage-baseline-2026-10-25.md`](../../../docs/audits/coverage-baseline-2026-10-25.md),
including a re-measurement after ticket 127 formatted the tree (32.5% → 28.5% from the line
denominator growing, with no test change).

Floors, each the baseline rounded down: global 26/18/20/25, `packages/domain/src/**`
91/78/90/89, `packages/contracts/src/**` 90/45/52/88, `apps/api/src/rate-limit/**`
57/54/58/54, `apps/api/src/app-context.ts` 50/30/42/49.

The gate was proven to bite at both tiers rather than assumed to:
`ERROR: Coverage for lines (32.53%) does not meet global threshold (95%)` and
`ERROR: Coverage for lines (95.14%) does not meet "packages/domain/src/**" threshold (99%)`.
It also bit for real: the pre-format global floor of 30 failed at 28.47% after formatting,
which is how the denominator shift was noticed instead of guessed.

**Not done — one criterion is only partly satisfied.** The ticket names
`apps/api/src/auth-session.ts` and `apps/api/src/ledger.ts`, and neither has a floor.
`ledger.ts` measures **exactly 0%** in the unit scope and is not untested:
`tests/unit/ledger.test.ts` covers `@diary/domain/ledger` at 95%+, while the
PostgreSQL-facing module is covered by three integration suites. `auth-session.ts` is 13.5%
for the same reason. A floor from a 0% baseline is not a floor, and one from a measurement
that structurally cannot see their tests would be a false guarantee. The prerequisite is a
coverage run that includes the integration suite, which needs PostgreSQL — unavailable here.
